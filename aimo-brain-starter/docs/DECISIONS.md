# Architecture Decision Log

Record each important decision with date, context, alternatives, decision and consequences. Do not silently replace protocol or infrastructure choices.

## ADR-001 — Independent agents, shared open protocols

**Decision:** Use separate buyer and supplier services with official A2A for inter-agent communication and official MCP for tools. Keep core role-neutral and domain schemas modular.

**Rationale:** Preserves organizational autonomy, external interoperability and future vertical expansion.

**Tradeoff:** More service, identity and workflow complexity than a single-process demo.

## ADR-002 — Managed first, portable by design

**Decision:** Railway for initial container services, Neon for Postgres, Vercel for portal; avoid provider-specific domain logic.

**Tradeoff:** Cloud management is simpler initially, but isolation and self-hosted compatibility require explicit testing.

## ADR-003 — Deterministic binding authority

**Decision:** LLM proposes; policy services and authorized business systems commit. Every commit references immutable terms and an idempotency key.

**Tradeoff:** More approvals and state transitions, substantially lower unauthorized-transaction risk.

## ADR-004 — M0 workspace layout and package naming (2026-11-17)

**Context:** Needed a concrete `uv` workspace and Next.js layout matching `docs/ARCHITECTURE.md`'s proposed repository layout.

**Decision:** Each app/package directory uses a hyphenated PyPI-style name (`buyer-agent`, `agent-runtime`, …) but installs an underscored importable module (`buyer_agent`, `agent_runtime`, …), per Python packaging convention. `industries/food-wholesale` installs as `aimo-food-wholesale` / `food_wholesale` to avoid colliding with a generic `food_wholesale` name on a shared index later. Packages not yet implemented in M0 (`identity`, `authorization`, `audit`, `a2a-integration`, `mcp-integration`, `worker`) exist as installable, importable boundaries whose functions raise `NotImplementedError` with the milestone that implements them, rather than any stub that could be mistaken for working code.

**Tradeoff:** Slightly more pyproject.toml boilerplate than a single flat package; in exchange, every service boundary from `docs/ARCHITECTURE.md` is real and independently installable from day one, and contract tests (`tests/contracts/test_database_isolation.py`) can statically verify no forbidden cross-service import exists.

## ADR-005 — Portal pinned to Next.js 16, ESLint flat config (2026-11-17)

**Context:** Next.js 14.2.15 (the version originally planned) has multiple disclosed CVEs with no 14.x patch resolving all of them per `npm audit`; only Next.js 16.x closes them. Next.js 16 also removed the `next lint` subcommand in favor of running ESLint directly, and ESLint 9's default flat config (`eslint.config.mjs`) replaces `.eslintrc.json`.

**Decision:** Portal uses Next.js 16.4.6, React 19.1.0, ESLint 9.39.5 with `eslint.config.mjs` spreading `eslint-config-next`'s flat config, and the portal's `lint` script runs `eslint .` directly. `npm audit` reports 0 vulnerabilities at this pin.

**Tradeoff:** Ahead of the `README.md`/`CLAUDE.md` "Next.js/TypeScript" stack entry's implied version; no API used by the M0 placeholder page is affected, but any portal code added in M6 should target the App Router conventions current to Next.js 16, not 14.

## ADR-006 — SQLite for fast local/unit tests, Postgres service containers in CI (2026-11-17)

**Context:** `docs/ARCHITECTURE.md` specifies Postgres (Neon in production, local Postgres via Docker Compose for dev) as the only persistence target; M0 needs tests that run without Docker/Postgres being available everywhere a contributor works.

**Decision:** Unit/contract/integration tests under each app's `tests/` and the top-level `tests/` directory point `DATABASE_URL`/`BUYER_DATABASE_URL`/`SUPPLIER_DATABASE_URL` at per-service temp-file SQLite databases (never `:memory:`, which does not share state across connections) by default. CI additionally provisions three real Postgres databases in a service container and runs every service's Alembic migrations against them, so the actual production dialect is verified on every push, not just structurally plausible SQL.

**Tradeoff:** A contributor without Docker running only `uv run pytest` does not get Postgres-dialect proof for free; they get it from CI. `docker compose up -d` plus the migration commands in `README.md` give the same proof locally if Docker is available.

## ADR-007 — A2A SDK integration specifics (2026-11-18, M1)

**Context:** `a2a-sdk` 1.3.0 (latest on PyPI, released 2026-10-27) was installed and its real API introspected directly (constructors, field names, enum values) rather than taken on faith from third-party tutorials, several of which describe older pre-1.0 or stale APIs. Key, non-obvious findings:

- The SDK's core types (`AgentCard`, `AgentSkill`, `Message`, `Task`, …) are **protobuf messages** (`a2a_pb2.*`), not Pydantic models. `Message.metadata` is a protobuf `Struct`, which supports `__getitem__`/`__contains__`/`__setitem__` but **not** `.get()` — calling `.metadata.get(...)` raises `AttributeError: get` only inside the running task, as an opaque JSON-RPC `InternalError`. Both executors use an explicit `"key" in message.metadata` check instead.
- `TaskState`/`Role` are plain `int`-backed `EnumTypeWrapper`s: a `Task.status.state` field value is a bare `int`, not an object with `.name`; converting to a readable string requires `TaskState.Name(value)`.
- `a2a.server.tasks.DatabaseTaskStore(engine: AsyncEngine, ...)` takes a plain SQLAlchemy async engine directly — it fits this project's own `database.new_engine()` factory with zero adapter code, and is used as the real task-persistence backend for both agents, bound to each agent's own database.
- `DatabaseTaskStore`'s non-default `table_name` dynamically declares a new mapped class (`create_task_model`) against the SDK's own shared `DeclarativeBase`, every time it is constructed with a non-`"tasks"` name. Since `create_app()` can run more than once per process (every test that boots a fresh app does this), a non-default `table_name` causes `sqlalchemy.exc.InvalidRequestError: Table '...' is already defined`. Both agents use the **default** `table_name="tasks"` for this reason; it never collides with this project's own `buyer_tasks`/`supplier_tasks` business task-log tables.
- The Agent Card's `AgentInterface.url` **must exactly match** the address the server is actually reachable on — the A2A client builds its transport from the resolved card's interface URL, not from the base URL used for discovery. `supplier_a2a_url`/`buyer_a2a_url` settings are therefore load-bearing, not cosmetic, and must be set correctly in every deployment (Railway services, CI, local dev) to the address the service is actually bound to.
- JSON-RPC routes (`create_jsonrpc_routes`) are mounted at `/` (root), matching the Agent Card's interface URL being the bare base URL — not at a `/a2a` subpath, which would mismatch the card and cause every send to 404.

## ADR-008 — Registry-api as a separate service; service credentials; SSRF defense (2026-11-18, M2)

**Context:** `docs/ARCHITECTURE.md` originally described a single "Network API / Registry" box owning organizations, agents, capabilities, relationships and trust status together. For M2, the user explicitly directed splitting this into two independently deployable services — `network-api` (organization identity, trading relationships, authorization to manage an org's own agents) and `registry-api` (agent registration, Agent Card validation, capability discovery, endpoint-ownership verification, lifecycle) — sharing a Neon Postgres *instance* at most, never a database, schema, role or direct table access.

**Decision — service split:** `registry-api` is a new, independently deployable FastAPI service (`apps/registry-api`) with its own database (`aimo_registry` locally/in CI), its own Alembic chain, its own Dockerfile, and its own Railway config. It owns exactly three tables: `registry_agents`, `registry_agent_capabilities`, `registry_audit_events`. It does **not** store organization records or trading relationships — those stay in `network-api`, which registry-api reaches only over HTTP (`registry_api.network_client.has_active_relationship`), authenticated with a shared internal-service key, never a database connection. This is the one cross-service call in the whole system; it is read-only and it never proxies the A2A conversation itself — discovery returns the supplier's real A2A endpoint URL, and the buyer talks to it directly with the official SDK.

**Decision — service credentials, not a new identity provider:** "Authorization to manage organization-owned agents" is network-api's responsibility per the split above, but registry-api must verify that authorization on every write without calling network-api synchronously (availability coupling) or sharing a database. `packages/identity` (previously a stub raising `NotImplementedError` for exactly this milestone) now implements short-lived, HMAC-signed, scope-bound service credentials: `network-api` mints one (`POST /organizations/{id}/service-credentials`, protected by a bootstrap admin key — there is still no human OIDC/approval flow; that is M6/M7) scoped to one organization and the `manage_agents` action; `registry-api` verifies it locally with a shared signing secret (`SERVICE_CREDENTIAL_SIGNING_SECRET`, must match exactly across both services). Rotating that secret immediately invalidates every outstanding credential. This is explicitly not OIDC and not a long-lived API key — `identity.verify_human_token` still correctly raises `NotImplementedError` for human authentication, which is unrelated and still out of scope.

**Decision — SSRF defense for Agent Card fetch:** registry-api is the one service that fetches an operator-supplied URL (`a2a_card_url`, and later the same host's `/.well-known/aimo-brain-challenge` for ownership verification). `registry_api.card_fetch` enforces, on every request: only `http`/`https` schemes (unconditionally — never bypassed); all resolved IP addresses checked against private/loopback/link-local (covers the `169.254.169.254` cloud metadata endpoint)/multicast/reserved/unspecified ranges; no redirects followed at all (a 3xx response is simply not a valid card response, so a redirect to a disallowed target is never reached by a second request); a response-size cap. A **documented residual limitation**: the IP check happens at request time but the subsequent TCP connection is not pinned to that exact address, so a DNS answer that changes between the check and httpcore's own resolution (DNS rebinding) is not fully closed — acceptable for M2 given there is no real external registration target yet, and stated here rather than silently assumed away.

**Decision — explicit, isolated dev/test bypass, not a disabled check:** buyer-agent/supplier-agent run on `127.0.0.1` in every local/CI environment this repository has, which the IP-range check would otherwise reject outright. `RegistryApiSettings.registry_allow_private_network_card_targets` (env `REGISTRY_ALLOW_PRIVATE_NETWORK_CARD_TARGETS`) skips *only* the IP-range check, never the scheme check, and defaults to `false`. Local dev (`.env.example`) and CI set it `true` explicitly; it must never be set in a real deployment. `tests/integration/test_registry_discovery_e2e.py::test_malicious_scheme_card_url_is_rejected_before_any_registration` proves the scheme check still rejects `file://` even with this bypass enabled, over real HTTP.

**Decision — discovery semantics:** `GET /agents` returns only agents that are `active` (not `pending`/`suspended`/`revoked`) and only those whose organization has an active trading relationship with the requesting organization — except an organization may always discover its own agents regardless of relationship state (self-discovery never calls network-api at all). The discovery response (`DiscoveredAgentOut`) is a minimal projection — `agent_id`, `organization_id`, `display_name`, `status`, `capabilities`, `a2a_endpoint_url` — deliberately excluding the raw Agent Card payload, verification challenge, and any credential material, per `docs/SECURITY.md`'s "no private Agent Card metadata or credentials through discovery."

**Decision — Agent Card is not identity:** registering a card only proves "something answers at this URL with this skill shape." Registry-identity (which organization owns this `agent_id`, and whether it is `active`) is a separate, registry-asserted fact, recorded only after the challenge-based endpoint-ownership check (`POST .../verification/start` then `.../confirm`, re-fetching `/.well-known/aimo-brain-challenge` through the same SSRF-safe transport) passes. `revoked` is a terminal state — a revoked agent cannot be reactivated, only re-registered as a new pending record.

**Decision:** Pin `a2a-sdk[http-server,fastapi]==1.3.0` on `buyer-agent`/`supplier-agent` only (never on shared `packages/*`). Each agent's own `DatabaseTaskStore` (default table name) against its own database is the real restart-recovery mechanism; each agent additionally keeps a lightweight `buyer_tasks`/`supplier_tasks` business task-log table (own Alembic migration) recording skill id, role and counterparty for queryability without depending on the SDK's internal schema.

**Tradeoff:** Tying the correctness of discovery to an exact advertised URL match is more operationally fragile than a path-relative scheme would be, but it is the SDK's actual contract, not a choice this project made.

## ADR-009 — MCP tool servers as separate per-organization services; scope-based tool authorization (2026-11-18, M3)

**Context:** M3 requires buyer-agent and supplier-agent to use business tools (catalogue, inventory, customer pricing, delivery options, purchase requirements, budget, approved suppliers, purchase approval) through the official MCP Python SDK rather than importing tool implementations directly. The official SDK (`mcp` on PyPI) was introspected directly rather than taken from tutorials, several of which describe the pre-1.0/early-1.x API: the current stable `FastMCP` API (pinned `mcp==1.30.0`, the latest 1.x release — `mcp` 2.x is a recent, larger restructure not yet adopted here) exposes `streamable_http_app()` returning a Starlette app with its own internal lifespan, and a `Context` object whose `request_context.request` is the real underlying Starlette `Request` for an HTTP-transport call.

**Decision — one MCP server per organization role, not a shared tool service:** `apps/buyer-mcp` and `apps/supplier-mcp` are new, independently deployable FastAPI services, each mounting a `FastMCP` server's Streamable HTTP ASGI app (`mcp.session_manager.run()` wired as the FastAPI app's own lifespan — the SDK's own documented pattern for "mounting multiple FastMCP servers in one FastAPI app"). Each owns exactly one database, holding only a `*_mcp_tool_invocations` audit table; the fictional catalogue/budget/etc. data itself lives in `industries/food-wholesale/adapters/mock`, imported only by these two services — never by `buyer-agent`/`supplier-agent` directly (enforced by `tests/contracts/test_database_isolation.py`).

**Decision — authorization reuses M2's service-credential mechanism, not a new one:** `network-api`'s existing credential-issuance endpoint (`POST /organizations/{id}/service-credentials`) gained a `scope` field, allowlisted to `manage_agents` (M2), `use_buyer_tools` and `use_supplier_tools` (M3). Each MCP server is configured with exactly one organization id it serves (`BUYER_MCP_ORGANIZATION_ID`/`SUPPLIER_MCP_ORGANIZATION_ID`) and one required scope; `packages/mcp_integration.server_auth.require_tool_scope` (shared by both servers) reads the bearer token directly off the real HTTP request via `ctx.request_context.request`, verifies it with `identity.verify_service_credential`, and rejects unless both the scope *and* the organization id match. A credential minted for the buyer's own tools is therefore structurally incapable of calling supplier-mcp — wrong scope and wrong org both fail it — with no per-tool access-control logic required. The agent process itself never holds the admin key needed to mint its own credential; an operator mints it out of band, matching how registry-api management credentials are obtained.

**Decision — rejection surfacing:** raising `mcp.server.fastmcp.exceptions.ToolError` inside a tool function is the correct way to reject a call (it becomes an `isError` tool result, not a transport failure) — but the SDK wraps any such exception as `"Error executing tool <name>: <message>"` before it reaches the client, so `mcp_integration.client`'s error classification matches `"Unauthorized:"` and `"validation error"` as substrings anywhere in the message, not as a prefix.

**Decision — client-side hardening against malformed/malicious responses:** the MCP SDK's own client-side output-schema validation (`ClientSession._validate_tool_result`) only checks a response against the *same server's own advertised* schema — a malicious server can lie consistently and pass that check. `supplier_agent.mcp_client.fetch_availability_matches` additionally catches `KeyError`/`TypeError` while consuming a tool's structured content and re-raises as `mcp_integration.McpMalformedResponseError`, so a compromised or buggy MCP server surfaces as a clear, typed failure rather than an opaque crash or a silently wrong business result (`tests/security/test_mcp_tool_security.py` proves this against a deliberately malformed rogue server).

**Decision — bounded retries, not unbounded or absent:** `mcp_integration.call_tool` retries only connection-level failures (`httpx.HTTPError`, `OSError`, `TimeoutError`, `ExceptionGroup`) up to a small bounded `max_attempts`, never a tool's own business-logic rejection — an unreachable MCP server raises `McpServerUnavailableError` within bounds rather than hanging.

**Tradeoff:** Pinning `mcp==1.30.0` (the last 1.x release) rather than the newly-released `mcp` 2.x avoids adopting a just-shipped, larger API restructure without an established usage pattern to verify against; revisit this pin once 2.x has more real-world precedent.

## ADR-010 — Negotiation reuses M0's lifecycle enum; two-step state transitions; sender/organization binding (2026-11-18, M4)

**Context:** M4 requires an explicit negotiation state machine (`requested`/`quoted`/`countered`/`proposed_agreement`/`rejected`/`expired`/`cancelled`) with enforced legal transitions, versioned immutable proposals, and a guarantee that no M4 code path can reach a binding state. `packages/trade-protocol` already had a complete, generic `TradeState` enum and `VALID_TRANSITIONS` table from M0 (`DISCOVERED → REQUESTED → PROPOSED ↔ NEGOTIATING → PENDING_AUTHORIZATION → AUTHORIZED → ...`), built for exactly this purpose but never previously exercised.

**Decision — reuse the M0 enum, map rather than rename:** M4's spec names map onto existing states (`requested`=`REQUESTED`, `quoted`=`PROPOSED`, `countered`=`NEGOTIATING`, `proposed_agreement`=`PENDING_AUTHORIZATION`, `rejected`/`expired`/`cancelled` unchanged) rather than introducing a second, parallel enum. `AUTHORIZED`/`COMMITTING`/`COMMITTED`/`FULFILLING`/`VERIFIED` remain legitimate *future* transitions in the generic table (M5's job), so "no M4 path reaches them" is enforced by static scanning of the M4 modules themselves (`tests/security/test_negotiation_security.py::test_no_m4_code_path_creates_a_binding_order_or_payment`), not by disabling those transitions in the shared table.

**Decision — a "quote" response always leaves the state at `PROPOSED`, regardless of round:** both the supplier's very first quote and every subsequent counter-quote use artifact type `quote` and land the negotiation back at `PROPOSED` — matching `VALID_TRANSITIONS`, which permits `NEGOTIATING → PROPOSED` just as it permits `REQUESTED → PROPOSED`. A buyer's `counterproposal` always moves the state to `NEGOTIATING` first (recording the buyer's own artifact and checking its `supersedes_proposal_id` against the current head — this is where staleness is actually caught), and the supplier's reply to it (quote/`proposed_agreement`/`reject_proposal`) is a second, separate transition out of `NEGOTIATING`. This two-step shape is required by the transition table itself: `PROPOSED → PROPOSED` and `NEGOTIATING → NEGOTIATING` are both illegal self-loops, so a single-step "receive counter, reply in place" design does not type-check against the existing table — discovered by writing `apps/supplier-agent/tests/test_negotiation_store.py`'s illegal-transition test before the handler logic, not after.

**Decision — `accept_proposal` skips straight to `PENDING_AUTHORIZATION` in one step:** unlike counterproposals, an acceptance is never persisted as its own intermediate transition — only the resulting `proposed_agreement` is, directly from whatever state the negotiation was actually in (`PROPOSED` or `NEGOTIATING` are both legal sources per the table). The accept message itself is validated inline (`accepted_proposal_id`/`accepted_content_hash` must exactly match the current head) without a database write of its own.

**Decision — sender/organization binding, found during this milestone, not assumed from the start:** a `negotiation_id` travels in plain, unencrypted A2A artifacts — it is not a secret. The first implementation of `supplier_agent.negotiation`'s counterproposal/accept/reject handlers validated only that the referenced `proposal_id` matched the current head, not that the *sender* was the organization the negotiation actually belongs to. This meant any organization that learned another buyer's `negotiation_id` (e.g. through logs, a shared registry, or simple guessing of a predictable ID scheme) could have injected a counteroffer, acceptance or rejection into a negotiation that was not theirs. Fixed by adding `_verify_counterparty` (checks `organization_id` and `sender_agent_id` against the negotiation's recorded counterparty before any mutation) to all three handlers, and proven with `tests/security/test_negotiation_security.py::test_cross_organization_cannot_hijack_anothers_negotiation` over real A2A HTTP before considering the milestone done.

**Decision — deterministic counteroffer evaluation, LLM output never decisional:** `food_wholesale.negotiation.evaluate_counterproposal` is a pure function over MCP-sourced reference prices and a fixed margin floor (`MINIMUM_MARGIN_FRACTION`), generic over an arbitrary set of line items. A below-floor offer is countered at exactly the floor price (there is nothing to split a difference over, since the supplier will not go lower) — an earlier version computed a "midpoint" that was always clamped back to the floor by construction, so the dead code was removed rather than left as a misleading no-op. `supplier_agent.negotiation._explain_counteroffer` calls the existing deterministic `FakeLLM` to attach a human-readable rationale string alongside a counter-quote, satisfying "reasoning may recommend a counteroffer" — but the string is never read by the decision function or any state transition, per CLAUDE.md's "LLM outputs are untrusted proposals."

**Decision — replay safety only where it is actually needed:** only `supplier_agent` gained an inbound-artifact dedup cache (`supplier_processed_artifacts`) — the supplier is the only side that receives potentially-retried messages (buyer-initiated, synchronous A2A request/response). `buyer_agent` records its own negotiation history for audit/recovery but does not need a receive-side dedup cache, since it never receives an unsolicited inbound negotiation message.

**Tradeoff:** The two-step transition dance for counterproposals is less obvious to read than a single combined step would be; the alternative (loosening `VALID_TRANSITIONS` to allow `PROPOSED → PROPOSED`) was rejected because it would also loosen M5's eventual binding-state guards for no real benefit here.

## ADR-011 — OPA as a bounded subprocess; credential-in-payload for M5 artifacts; agent-scoped credentials; evidence-then-commit over the existing A2A channel (2026-11-19, M5)

**Context:** M5 requires real OPA policy decisions, durable human approval, independently-verified two-sided authorization and idempotent commitment, without inventing a parallel transaction state machine, a new transport, or unnecessary new infrastructure. The architecture was presented and approved before any M5 code was written (see the M5 architecture-review turn in-session), covering service boundaries, the authorization trust model, OPA policy structure, the approval data model, commitment state transitions, idempotency/recovery design, and the required test matrix.

**Decision — OPA via a bounded `opa eval` subprocess, not a server:** `packages/policy-engine` (new) shells out to the real `opa` CLI binary (`opa eval --data <bundle_dir> --stdin-input --format json <query>`) with a bounded timeout, rather than running `opa run --server` as a long-lived sidecar. This matches the "no unnecessary new infrastructure" constraint — one subprocess call per decision needs no new network service, no new Docker image, no health-check wiring. Every failure mode (binary missing, timeout, non-zero exit, unparseable or structurally invalid output) is turned into an explicit `allow=False` decision inside `evaluate_policy()` itself, so no caller can forget to fail closed. `packages/authorization.evaluate_binding_action` builds the generic input and calls this; `industries/food-wholesale/policies/{buyer,supplier}/v1/` hold the only business-specific content (budget limits, approved suppliers/customers, margin/quantity thresholds, human-approval thresholds) — core never sees a SKU. The `opa` binary itself is a dev/CI dependency (downloaded from `openpolicyagent.org`, not committed to the repo); CI must fetch it the same way before running the test suite, exactly as it already provisions Postgres service containers.

**Decision — the sender's credential travels inside the artifact payload, not as A2A message metadata:** the original plan attached a bearer credential as `Message.metadata["authorization"]` on the *sending* side only. This does not work for the supplier's reply: the A2A exchange here is synchronous request/response (the buyer always initiates, per the existing `buyer_agent.client` pattern from M1–M4), so a supplier's answer comes back as a `Task`'s artifacts, which have no sender-message-metadata channel of their own. `authorization_evidence`/`order_commit_request`/`order_confirmation` therefore all carry a `credential` field *inside* their JSON Schema payload (required field, added to all three new schemas) — symmetric for both directions, verified by the receiver with `identity.verify_service_credential` before `organization_id`/`sender_agent_id` are trusted at all. This was discovered during implementation, not anticipated in the original architecture review, and is the one deviation worth recording explicitly.

**Decision — new agent-scoped credential fields and scopes, additive to M2's mechanism:** `ServiceCredentialClaims`/`issue_service_credential`/`verify_service_credential` gained optional `agent_id` and `approver_id` fields (backward compatible — M2/M3's `manage_agents`/`use_buyer_tools`/`use_supplier_tools` credentials are unaffected). Four new scopes: `negotiate` (reserved for a future retrofit onto M4's own messages — not used yet), `commit` (bound to one `agent_id`, used by both agents' M5 artifacts), `approve` (bound to one `approver_id`, used by the human-approval decision endpoint), `execute_order` (organization-scoped only, used by supplier-mcp's execution tool). `network-api`'s credential-issuance endpoint validates that `commit`/`negotiate` credentials carry an `agent_id` and `approve` credentials carry an `approver_id` before minting.

**Decision — evidence-then-commit as two request/response round trips over the existing direct A2A connection, buyer-driven:** no new transport, no new service, no inbound executor added to `buyer-agent` (it remains a client-only "status" responder for A2A, per M1). Round trip 1: buyer sends its own `authorization_evidence`; `supplier_agent.commitment.handle_authorization_evidence` records it (credential-verified), independently evaluates the supplier's own OPA policy for the identical `content_hash`, and replies with the supplier's own evidence (or `allow=False, deny_reason="human_approval_pending"` if its own human approval is still outstanding — a *retryable* state, not a terminal denial). Round trip 2, only once `authorization.is_mutually_authorized` is true on the buyer's side: an idempotent `order_commit_request`; `supplier_agent.commitment.handle_order_commit_request` re-verifies mutual authorization independently on its own side too (never trusting that the buyer's claim alone is sufficient), calls `supplier-mcp`'s `execute_order` tool, and replies with `order_confirmation`. **The exact point a simulated transaction becomes binding is `order_confirmation.payload.status == "CONFIRMED"`** — not the earlier mutual-authorization state (`AUTHORIZED`), and not the buyer's commit-intent send (`COMMITTING`). `evaluate_and_request_approval`/`record_counterparty_evidence` are both idempotent (re-entrant calls return the already-finalized row rather than re-evaluating or duplicating it; a not-yet-allowed counterparty row is updated in place when a later message reports a newer decision for the *same* content_hash, rather than left stale or duplicated) — found necessary when the end-to-end test called the commitment flow twice to prove idempotency and hit a `MultipleResultsFound` from a naive unconditional insert.

**Decision — idempotency authority lives in `supplier-mcp`, not `supplier-agent`:** the idempotency key (`sha256(content_hash + buyer_org + supplier_org)`, deterministic, never regenerated per attempt) is enforced by a UNIQUE database constraint on `supplier_mcp_orders.idempotency_key` plus an `IntegrityError` race-recovery path (two concurrent identical commits: the loser reads back the winner's row rather than erroring) — this is the actual "approved mock order adapter," reusing M0's `food_wholesale.adapters.mock.order_api.MockOrderApi` as the simulated external system underneath it. `supplier-agent`'s own `supplier_orders` table is a durable audit copy, not a second idempotency authority.

**Decision — scope narrowing left for the M4 negotiation messages (documented, not fixed):** `request_for_quote`/`quote`/`counterproposal`/`accept_proposal`/`reject_proposal` still trust their payload's `organization_id`/`sender_agent_id` the way M4 left them (ADR-010's `_verify_counterparty` check, not a cryptographic one). Only the M5 artifacts verify a credential. This bounds the size and risk of the M5 change (no M4 code path or its passing tests were touched for this) at the cost of leaving the negotiation phase itself spoofable by anyone who learns a `negotiation_id` — never a path to an actual commitment, since that always requires a verified `commit` credential, but a real availability/annoyance vector worth closing in a follow-up.

**Tradeoff:** the credential trust root is still one shared HMAC secret across every service in the deployment (ADR-008's pattern, now extended to agent-scoped and approver-scoped credentials) — explicitly not production multi-organization PKI; see `docs/SECURITY.md`'s new M5 section for the full, undiluted statement of this limitation. Human approval is a pre-registered `approver_id` behind a service credential, not OIDC/MFA — M6/M7 scope. `apps/worker`'s scheduled dispatch/reconciliation loop remains a scaffold; M5 ships the idempotent, re-callable building block (`run_authorization_and_commitment`) a future scheduler would call, not the scheduler itself.

## ADR-012 — Per-artifact JWS signatures replace the cross-organization HMAC trust root; registry-api gains a direction-agnostic sender-verification endpoint; a labeled dev-OIDC approval adapter; idempotent worker recovery (2026-11-20, M5.1)

**Context:** M5 closed the *scoping* gap in cross-organization authentication (agent-scoped credentials, evidence bound to exact hashes) but left the actual trust root as one shared HMAC secret (`SERVICE_CREDENTIAL_SIGNING_SECRET`) — anyone who learned it could forge a `commit`/`negotiate`/`approve` credential for *any* organization. M5.1's explicit brief: authenticate every RFQ/quote/counteroffer/proposed-agreement/commitment message (not just M5's three new types), eliminate the shared-secret trust root in favor of independently-verifiable asymmetric identities, remove raw bearer credentials from persisted business artifacts, add a real (if simulated) human-approval identity, and implement durable crash/retry recovery via `apps/worker`. The architecture (JWS envelope, key-discovery model, trust boundaries, verification flow, security tests) was presented and approved before any M5.1 code was written, after an explicit redirect from an initially-proposed bearer-JWT-per-call design to per-artifact signatures — recorded below because it changed the design mid-review, not after.

**Decision — per-artifact JWS `proof`, not a bearer token on the A2A transport:** every negotiation/authorization/commitment artifact (`request_for_quote`, `quote`, `counterproposal`, `accept_proposal`, `reject_proposal`, `proposed_agreement`, `authorization_evidence`, `order_commit_request`, `order_confirmation` — nine schemas, all of them) gained an optional-in-schema, enforced-at-runtime `proof` object: `{"alg": "EdDSA", "kid": ..., "jws": ...}`. The signed JWS payload is `{iss, sub, aud, neg, typ, ver, hash, artifact_digest, jti, iat, exp}`, where `artifact_digest` is `sha256(canonicalize(artifact-without-proof))` reusing `trade_protocol.negotiation`'s exact canonicalization rule (sorted-key, no-whitespace JSON — one rule in the whole codebase, never two). `packages/message-integrity` (new) owns `sign_artifact`/`verify_artifact_proof` and is otherwise industry-independent. The original architecture review proposed a bearer JWT attached as the A2A `Authorization` header via the SDK's own `ClientCallInterceptor`/`ServerCallContextBuilder` extension points (confirmed to exist in `a2a-sdk` 1.3.0 by direct introspection); the user explicitly redirected this to per-artifact signatures instead, reasoning that a signature bound to the artifact's own content is a stronger, more durable guarantee than a token authenticating only the call, and that it travels identically in both directions without needing SDK-level request/response plumbing — a problem M5's credential-in-payload design had already run into once.

**Decision — found during implementation, not anticipated: A2A's protobuf `Struct` transport coerces every JSON number to double-precision float.** `version: 1` (int) sent by the buyer arrived at the supplier as `version: 1.0` (float), which `json.dumps` serializes differently (`"1"` vs `"1.0"`), breaking every digest check across the wire. Since every monetary/quantity value in this codebase is already a decimal *string* (`docs/PROTOCOLS.md` rule 2), the only legitimate JSON numbers an artifact ever carries are integers; `message_integrity.proofs._normalize_numbers` now recursively converts any float with a zero fractional part back to `int` before canonicalizing for a digest, both when signing and when verifying. This is a general fix for anything built on this transport, not a one-off patch for `version`.

**Decision — organization-level Ed25519 keys; `network-api` becomes a JWKS-only directory:** one keypair per organization (not per-agent — the organization vouches for which of its own agents, via the JWT's `sub` claim, may use it), generated out-of-band by `scripts/generate_signing_key.py`. New `organization_signing_keys` table and three endpoints on `network-api`: `POST /organizations/{id}/signing-keys` (register a public JWK), `POST .../signing-keys/{kid}/revoke` (immediate; revoked keys are excluded from the next line), `GET /organizations/{id}/jwks.json` (public, unauthenticated, standard RFC 7517 JWKS of every currently-valid key). `network-api` never receives or stores a private key — losing this service's data now only ever leaks public material, a categorical fix for M5's shared-secret weakness. `packages/identity`'s `commit`/`negotiate`/`approve` HMAC scopes were removed from `network-api`'s `ALLOWED_SERVICE_CREDENTIAL_SCOPES` entirely (the underlying `agent_id`/`approver_id`-aware HMAC primitive in `packages/identity.tokens` itself was left in place as a harmless, still-generic building block, just unused for this purpose now). `use_buyer_tools`/`use_supplier_tools`/`manage_agents`/`execute_order` are unchanged — those are intra-organization (an agent calling its own org's MCP server, or network-api/registry-api talking to each other), not the cross-organization gap this ADR closes.

**Decision — registry-api gains `GET /agents/{id}/verify-sender`, a direction-agnostic check, rather than overloading M2's `/agents` discovery:** M2's discovery endpoint always treats the requester as the buyer side (`has_active_relationship(buyer=requesting_org, supplier=record.org)`), which is correct for catalog discovery but wrong for message authentication — a supplier verifying an inbound buyer message is not "discovering" anything, and the existing endpoint returned 404 for every legitimate buyer sender once supplier-side verification started calling it (found by running the first M5.1 end-to-end test, not anticipated in the design review). The new endpoint checks agent registration status independently of role and checks the trading relationship in *both* orderings. `buyer_agent.registry_client`/`supplier_agent.registry_client` (the latter new — the supplier previously never needed a registry client, only the buyer did discovery) both call it from a shared verification flow: signature -> JWKS -> digest/scope match -> replay (new `*_seen_message_proofs` table, one row per `jti`, independent of M4's `artifact_id`-keyed dedup cache, which still exists for a different purpose — see below) -> registered+active sender -> trading relationship -> (if the negotiation already has a recorded counterparty) exact participant match.

**Decision — replay protection is layered, not merged:** M5.1's `jti`-based check (one row per signed *message*, rejecting a literal resend of the exact same signed bytes) and M4's `artifact_id`-based cache (one row per logical *artifact*, returning the same cached business response for a legitimate retry that re-signs the same content under a fresh `jti`) serve different purposes and were kept separate rather than collapsed into one mechanism. A security test originally written to resend one signed object twice had to be corrected to re-sign before each send, once it became clear that was testing jti-replay-rejection rather than M4's intended artifact-level idempotency — the realistic "buyer retries after a timeout" case always re-signs (a fresh `jti`/`exp` is the entire point of bounding a signature's validity window) while keeping the same `artifact_id`/content.

**Decision — a labeled development identity adapter for human approval, not a bare credential:** `identity.dev_oidc` issues an ID-token-shaped JWT (`iss = "dev-oidc:<organization_id>"`, `sub = approver_id`, `roles: ["approver"]`), signed with that organization's own existing Ed25519 key (approver and verifier are always the same organization, so no cross-org JWKS lookup is needed here — simpler than message proofs). The `dev-oidc:` issuer prefix makes the token structurally unmistakable for a real OIDC provider. `decide_approval` (both agents) refuses every approval outright outside `environment in {"local", "staging", "test"}` — production has no identity provider configured, and this is never silently bypassed. `buyer_approvals`/`supplier_approvals` gained an `approver_issuer` column (migration `0005`, alongside the new `*_seen_message_proofs` table) so the audit trail always shows plainly that no real IdP was used.

**Decision — `apps/worker` becomes real, role-parameterized, calling back into the agent's own already-idempotent logic rather than reimplementing it:** `WORKER_ROLE=buyer|supplier` selects which agent package's commitment logic a given deployment serves, against only that role's own database — the same separate-deployable-process boundary the agents themselves hold, achieved here as two differently-configured deployments of one package rather than two codebases. The buyer role retries `buyer_orders` rows stuck in `COMMITTING`/`RECONCILIATION_REQUIRED` past a backoff, bounded by a durable per-row `attempts` counter (now incremented on every retry, not just the first attempt — `buyer_agent.commitment._commit` gained this), by re-invoking `buyer_agent.commitment.run_authorization_and_commitment` — the exact entry point a live request already uses, never a separate "worker version" of the commit logic. `_commit` also now explicitly catches `AgentUnavailableError`/`TaskNotCompletedError` from a commit-request send and converts them to `CommitmentError` rather than letting them escape uncaught — a timeout leaves the row at `COMMITTING` for the next cycle, never assumed to mean failure. The supplier role is a documented no-op for now: supplier-side commit handling is synchronous and request-driven, and already reports `RECONCILIATION_REQUIRED` on an ambiguous `execute_order` outcome; a supplier-initiated retry loop is a stated follow-up, not yet needed since the buyer is the only side that ever initiates a commit.

**Tradeoff:** organization-level (not per-agent) signing keys mean a compromised agent process can sign on behalf of its whole organization, not just itself — acceptable for now since each organization in this reference deployment runs exactly one agent per role, revisit if that changes. M4's own negotiation artifacts are now *also* covered by signature verification (unlike M5, which only signed its own three new types) — this was effectively free once verification was centralized at one call site per side (`a2a_executor.execute` for the supplier, `client._send_negotiation_artifact` for the buyer) rather than per-handler.

**Verified test run:** `uv run pytest -q` -> **268 passed**, run multiple times with no flakiness. New coverage: `packages/message-integrity/tests` 11 (valid proof, missing proof, tampering, scope mismatch, wrong audience, unknown/impersonating/revoked key, expired proof, key rotation, re-signing an already-signed artifact rejected), `packages/identity/tests/test_dev_oidc.py` 5, `apps/network-api/tests` signing-key register/fetch/duplicate/revoke/admin-key-required (5, replacing the two obsolete negotiate/approve-scope tests), `apps/buyer-agent/tests/test_authorization.py` and `apps/supplier-agent/tests/test_authorization.py` rewritten for verified-proof/dev-OIDC-token semantics (13 and 14), `tests/integration/test_authorization_commitment_e2e.py` and `test_negotiation_e2e.py` extended with real signing-key generation/registration and buyer-agent registry registration (previously only the supplier needed to register), `tests/security/test_negotiation_security.py` rewritten to sign every artifact with a real, registered key (5), `tests/integration/test_worker_recovery_e2e.py` (new, 1): a full real-HTTP flow through mutual authorization, a directly-injected stale `COMMITTING` row simulating a crash, `worker.run_dispatch_cycle` recovering it to `CONFIRMED`, a second cycle confirmed to be a no-op, and independent verification against `supplier-mcp`'s own idempotency table that exactly one order was ever created. `uv run ruff check . --no-cache` -> All checks passed. `uv run ruff format --check .` -> clean. `uv run mypy apps packages industries` -> Success, 84 source files. ## ADR-013 — Portal as a backend-for-frontend; a reused JWS trust chain for human approval; organization membership on network-api (2026-11-20, M6)

**Context:** M6's brief: real OIDC enterprise authentication (Entra ID-compatible), organization membership/roles, agent management, policy catalog/dry-run/activation, a human approval queue, negotiation monitoring, trading relationships and audit/evidence — reusing `apps/portal`'s existing Next.js shell and the existing backend services, adding backend APIs only where those services lacked the needed functionality, and never letting the portal bypass OPA or the existing commitment protocol. The architecture (authentication design, role matrix, API changes, data model, page structure, acceptance tests) was presented and approved before any M6 code was written.

**Decision — the portal is a backend-for-frontend holding every secret server-side, never a thin client:** all OIDC validation, session issuance, role resolution and backend calls happen in Next.js Route Handlers/Server Actions/Server Components; the browser only ever sees an opaque session cookie. This was the one way to satisfy "the browser never holds a service credential or signing key" while still letting the portal act as a real client of network-api/registry-api/buyer-agent/supplier-agent's existing credential-gated APIs.

**Decision — the portal gets its own tiny database, holding only sessions and its own audit log, via Node's built-in `node:sqlite`:** no organization/agent/negotiation/approval/order data is ever duplicated here — every page fetches it live from the service that owns it, matching every other milestone's "no cross-service database access" rule applied to a new consumer rather than a new producer. `node:sqlite` (stable from Node 22) was chosen over `better-sqlite3` after the latter's native build failed in this environment (no Visual Studio C++ toolchain available for `node-gyp`) — rather than work around a native dependency, the built-in module was used instead, which also meant bumping the portal's CI job from Node 20 to 22 (itself one of the explicit M6 asks: eliminate remaining Node 20 deprecation warnings, here via the only mechanism that could, a version bump this milestone actually needed for a different reason).

**Decision — organization membership and OIDC-tenant mapping belong on `network-api`, not a new service:** `network-api` already owns organization identity (ADR-008); a new `organization_members` table (`admin`/`operator`/`approver`/`auditor`, one row per role so "who can approve for org X" is a direct query) and `organizations.oidc_issuer`/`oidc_tenant_id` columns extend that ownership rather than inventing a second source of truth for who belongs to an organization. `GET /members/lookup` (internal-service-key) is queried fresh — never cached on the portal session — by both the portal (resolving a signed-in human's roles) and, critically, by the deciding agent itself (see below). The portal's `/members` admin page reuses the network admin key the same way `service-credentials`/`signing-keys`/`relationships` already do in this reference deployment; the portal itself independently confirms the caller holds the `admin` role before forwarding any admin-gated call, exactly as the field docstring on `network_admin_api_key` always said a pre-M6 consumer would need to.

**Decision — human approval reuses M5.1's JWS/JWKS machinery end to end, rather than adding a second cryptographic trust mechanism:** the portal is issued its own Ed25519 keypair and registered the same way any organization's is — against a new, non-trading pseudo-organization (`org_aimo_portal`, seeded in `network_api.seed`) through the *existing* `/organizations/{id}/signing-keys` and `/jwks.json` endpoints. No network-api code changed to support this; it was purely a seeding/registration decision. `identity.portal_approval` (new, structurally parallel to `identity.dev_oidc`) issues a short-lived (120s) assertion bound to the exact `organization_id`/`negotiation_id`/`content_hash` being decided, after the portal has itself verified a real OIDC session and checked (fresh) that the subject holds the `approver` role. `buyer_agent.authorization.decide_approval`/the supplier equivalent now peek the token's `iss` claim to dispatch between the unchanged dev-OIDC path and a new portal-assertion path; the portal path verifies the assertion's signature against the portal's own JWKS entry, confirms every bound claim matches the approval being decided, and then makes its **own** fresh `/members/lookup` call before honoring the decision — the assertion is proof the portal asked, never by itself proof the action is authorized. This was the deliberate design choice from the architecture review (reuse M5.1's primitive, add independent agent-side revalidation) rather than, e.g., having the agent trust the portal's own check blindly.

**Decision — a new, narrow `manage_organization` service-credential scope, not new per-capability scopes:** the portal calls each organization's own buyer-agent/supplier-agent through a new, additive `/management` FastAPI router (mounted on the same app as the A2A routes, no new service), authorized by a `manage_organization`-scoped credential minted fresh per call from `network-api` — intra-organization, like `execute_order`/`use_buyer_tools`, never crossing an organization boundary, so the existing shared-HMAC service-credential mechanism remains appropriate (unlike the cross-organization case ADR-012 moved off HMAC entirely). Admin-only management actions (policy activation) are gated by network-api only minting the credential with a fixed `agent_id="portal-admin-action"` sentinel when `scope=="manage_organization"` — reusing the existing `agent_id`-binding field on service credentials (never removed, just unused for cross-org purposes since ADR-012) for a new, narrowly-scoped M6 purpose, rather than adding a second credential type for one admin check.

**Decision — policy bundles remain filesystem-immutable; only a version *pointer* is portal-controlled:** `buyer_active_policy_pointer`/`supplier_active_policy_pointer` (one row per organization) override `settings.buyer_policy_version`/`supplier_policy_version` when present, falling back to the static default otherwise. `evaluate_and_request_approval` resolves the active version through this pointer on every call. `POST /management/policy/activate` (admin-only) writes it, audited; `POST /management/policy/dry-run` evaluates sample terms read-only against any on-disk version, writing nothing. No Rego editor was built — exactly the stated scope boundary.

**Decision — dual control via a decision child table, not a second approval record:** `buyer_approval_decisions`/`supplier_approval_decisions` (unique on `(approval_id, approver_id)`) let an organization configure `BUYER_REQUIRE_SECOND_APPROVER_ABOVE_AMOUNT`/the supplier equivalent; above that total, one approver's decision leaves the parent `BuyerApprovalRecord` at `PENDING` until a second, distinct approver also decides. The UNIQUE constraint is also the literal single-approver self-approval guard (the same person cannot decide twice) — a more elaborate "cannot approve your own initiated action" control was explicitly not built, since approvals in this system are policy-generated, not person-initiated, so there is no separate proposer identity for a real check to compare against; inventing one would have been exactly the kind of pretended-unimplemented-feature CLAUDE.md rules out.

**Decision — `request.nextUrl.origin`/`request.url` cannot be trusted for self-referential redirects under `next start`:** discovered while making the dev-login round trip actually work end to end — Next.js deliberately does not reflect the inbound `Host` header into these fields (hardening against host-header injection), always resolving a fixed `localhost`-shaped origin instead. A session cookie set for the real connecting host (e.g. `127.0.0.1`, as both curl and Playwright use) is then not sent back by the browser when a redirect's `Location` points at the differently-named `localhost` origin — two different origins for cookie purposes, so the session appeared to "not exist" immediately after a successful login. Fixed by adding `config.portalPublicUrl` (`PORTAL_PUBLIC_URL`), an explicitly configured origin used for every self-referential absolute redirect (`login`/`callback`/`dev-login`/`logout` routes), never derived from the request. A real deployment sets this to its real public URL; the test/CI configuration sets it to match the exact host Playwright/curl actually connects to.

**Decision — the browser-level test drives a minimal, real backend, not a mocked one:** `tests/e2e/serve_portal_demo.py` boots real `network-api`/`buyer-agent` servers (reusing the same `start_server`/`a2a_server_harness` real-uvicorn-in-a-thread pattern every Python integration test already uses) and seeds one pending approval directly into buyer-agent's own database — deliberately skipping supplier-agent/registry-api/OPA, since the Playwright spec's job is to prove the portal's own login/approval UI against real backend contracts, not to re-prove the negotiation/policy protocol underneath, which hundreds of existing Python tests already cover. `apps/portal/playwright.config.ts`'s `webServer` array starts this script and a production `next start` together; `tests/integration/test_portal_backend_e2e.py` separately proves the same HTTP contract from Python, including that revoking an approver's role takes effect on the very next decide attempt, independent of the frontend entirely.

**Tradeoff:** the portal holds `network-api`'s admin key and internal-service key directly — compromising the portal's server process is equivalent to compromising an operator's own backend tooling, not merely a UI. This is an accepted, explicitly-documented limitation for this reference/managed deployment model (see `docs/SECURITY.md`'s M6 section), not a gap assumed away. The real-OIDC code path is implemented against the standard protocol but was not live-tested against an actual Entra ID tenant in this sandbox — only the environment-gated development login adapter is exercised by the automated suite.

**Context:** M7's brief: make AIMO BRAIN ready to integrate with a real external supplier's business systems through an independently deployable, secure adapter architecture, with Valio Aimo as the intended first pilot but no access, credentials or sandbox endpoint for it. Before M7, `apps/supplier-mcp`'s tool handlers called `food_wholesale.adapters.mock` functions directly — there was no interface a real ERP adapter could implement instead, and `apps/worker`'s supplier role was a documented no-op (ADR-012).

A reusable behavioral contract suite (`business_system_integration.contract_tests.assert_adapter_contract`) is run against every implementation (mock, sandbox) to prove they are actually interchangeable — the entire point of the interface.

**Decision — `apps/supplier-mcp` resolves an adapter via a small factory keyed by `SUPPLIER_BUSINESS_SYSTEM_ADAPTER` (default `"mock"`), not a second tool surface:** `search_catalogue`/`check_inventory` keep their exact M3-M6 merged shape (catalogue search embedding today/tomorrow stock and price) *only* for the default `mock` adapter, preserving `supplier_agent.mcp_client.fetch_availability_matches`'s existing fallback-field behavior unchanged; `get_customer_price`/`get_delivery_options`/`execute_order`/`get_order_status` route through the adapter uniformly for every configured kind, since their existing output shapes already matched the generic one almost exactly. `execute_order`'s own DB-first idempotency authority (`supplier_mcp_orders`, UNIQUE `idempotency_key`) is unchanged by this milestone — it now calls `adapter.submit_order(...)` instead of the mock order API directly, and a `"pending"` `OrderSubmissionResult`/an `AdapterUnavailableError` both map to the existing `RECONCILIATION_REQUIRED` outcome, never `FAILED` (closing a real, found-during-this-milestone gap: `supplier_agent.commitment._record_order` was assigning to a `status` attribute that does not exist on `SupplierOrderRecord` — the field is `state` — so a previously-recorded order's row was silently never updated on a retry; fixed alongside adding the attempts/history bookkeeping below, since both needed the same code path touched). `external_order_id` becomes nullable (`supplier-mcp` migration `0003`) to represent a delayed-ack order honestly rather than fabricating a placeholder.

**Decision — a new standalone service, `apps/supplier-sandbox-erp`, is the proof vehicle, not an enhanced in-process mock:** the milestone explicitly asked for something that "behaves like an external ERP/API system" with customer-specific prices, stock that changes, delivery cutoffs, substitutions, MOQ, transient errors/timeouts, duplicate submissions and delayed acknowledgements — properties that only mean something tested against a genuinely separate process and database, reached over real HTTP with its own network-api-minted `use_sandbox_erp`-scoped credential (the same intra-organization HMAC trust root every other AIMO-internal call uses, not a new mechanism). A clearly-labeled, environment-gated `/admin/fault-injection` surface (mirroring `identity.dev_oidc`'s gating) arms one-shot transient-error/timeout/delayed-ack scenarios so tests are deterministic rather than relying on flaky randomization — this repo's standing no-flakiness norm extended to a new kind of fault, not relaxed for it.

**Decision — the Valio Aimo adapter is a documented boundary, not a scaffold with guessed behavior:** `food_wholesale.adapters.valio_aimo.ValioAimoAdapter` implements the same Protocol with every method raising `NotImplementedError`, each naming the exact missing access/identifier/mapping decision in the new `docs/integrations/valio-aimo-adapter-contract.md`. A static architectural test (`tests/contracts/test_database_isolation.py::test_valio_aimo_adapter_makes_no_network_calls`) asserts it imports no HTTP client at all — a stronger guarantee than a docstring, since it cannot regress into a real network call without that test failing first. `docs/integrations/valio-aimo-pilot-readiness.md` is the separate, partner-facing package for Valio Aimo's own stakeholders (architecture, required API capabilities, auth/security model, data flow/ownership, integration options, sandbox testing, deployment model, operational responsibilities, pilot acceptance criteria) — written for that audience, not as internal engineering notes.

A new `supplier_order_reconciliation_events`/`buyer_order_reconciliation_events` table on each agent (migration `0007` on both) records every attempt, not just the latest — the portal's new "reconciliation history" view reads this directly; the existing `attempts`/`last_error` columns only ever held the current count/last message, never a list.

## ADR-015 — Private-key-control challenge at agent registration; a cross-language JWS specification with signed test vectors (2026-11-24, M8 slice 1)

**Context:** M8's brief (external agent interoperability) needs two things before any independent, non-AIMO-hosted agent can meaningfully participate: (1) a specification of today's per-artifact JWS signature mechanism (`packages/message-integrity`, ADR-012) precise enough for someone with no access to this repository's Python code to implement a conformant signer/verifier, and (2) closing a real gap in `apps/registry-api`'s identity verification — it has, since M2 (ADR-008), proven only that a registrant controls the *endpoint* named by its Agent Card (the `/.well-known/aimo-brain-challenge` fetch), never that it controls the *private key* behind whatever signing identity it will use. Anyone who can stand up a web server at a URL could otherwise register that URL under any claimed signing key. This is the first of several planned M8 slices; the fuller M8 architecture (per-agent delegated signing keys chained to an org root, key rotation with substitution-on-rotation proof, a historical key archive for after-the-fact audit, an independent non-Python reference agent) was reviewed and approved before this slice, and is explicitly **not** built yet — see "Deferred to later M8 slices" below.

**Decision — a prose specification plus committed, language-neutral test vectors, not just better docstrings:** `docs/specs/jws-artifact-signatures.md` restates `message_integrity.proofs`' canonicalization rule, the float/integer normalization rule (`_normalize_numbers`, needed because A2A's protobuf `Struct` transport coerces every JSON number to a double), the exact JWS claim shape, and the normative verification order, byte-for-byte, with no reference to this repository's Python symbols beyond pointing at the reference implementation for cross-checking. `docs/specs/test-vectors/` holds four fixed JSON files (a full verify-success case with precomputed signature and recovered claims, a tampered-artifact verify-failure case, a wrong-key verify-failure case, and an integer/float digest-equivalence case) with permanently-far-future expiry so they never go stale. `packages/message-integrity/tests/test_jws_vectors.py` loads these same files and asserts the Python implementation produces/accepts exactly what they state — both a regression test and proof the vectors are accurate against the one implementation that exists so far.

**Decision — private-key-control is additive to, never a replacement for, endpoint-control:** `RegisterAgentIn.signing_public_key_jwk` (optional) lets a registrant supply an Ed25519 JWK at registration (`RegistryAgentRecord.signing_public_key_jwk`, migration `0002`, nullable). When set, `POST .../verification/confirm` additionally requires `key_proof_signature` — a signature over the pending challenge string made with the matching private key, verified with `message_integrity.keys.public_key_from_jwk` plus a raw Ed25519 `.verify()` call — before activation; the existing endpoint-ownership fetch still runs unconditionally. An agent that never supplies a signing key (every M0-M7 agent, and any future one that doesn't opt in) keeps the original endpoint-control-only behavior byte-for-byte unchanged — nothing about this slice is a breaking change to an existing registration flow.

**Decision — a basic key-substitution guard at re-registration, not yet a rotation flow:** once an `agent_id` has a signing key on file, re-registering it with a *different* key is rejected outright (409) rather than silently accepted — otherwise anyone who can pass the (comparatively weak) endpoint-ownership challenge again could hijack an already-established signing identity. Re-registering with the *same* key remains fine (idempotent, matching the existing re-registration semantics for display name/card URL). This is deliberately the simplest fail-closed rule that closes the obvious hijack path; it is not the rotation design from the approved M8 plan (proving control of the *current* key to authorize moving to a new one) — that is explicit, separately-tracked follow-up work, not an oversight.

**Deferred to later M8 slices, named explicitly rather than silently skipped:** per-agent delegated signing keys chained to an organization root (today's model stays organization-level, per ADR-012, unchanged); a real key-rotation endpoint requiring the *current* key's signature to authorize a new one; a historical key archive for verifying a since-rotated key's signature after the fact (today's JWKS resolver still only ever answers "is this key currently valid," per ADR-012's "revocation by absence" design); the independent, non-Python reference agent; and the public OpenAPI/Trust Extension descriptor publication. None of these are implemented by this slice.

**Tradeoff:** the key-substitution guard has no escape hatch yet — an organization that registered the wrong public key for an agent has no way to correct it except contacting an operator directly (no self-service rotation exists), which is acceptable friction for a slice whose job was closing the hijack path first, not maximizing convenience.

**Verified test run (original slice, superseded by the remediation below):** `uv run pytest -q` → **332 passed** (323 M0-M7 baseline plus 9 new). This was the state reviewed and sent back for remediation — see ADR-016 for what the review found and what was fixed before this slice is eligible for commit.

## ADR-016 — M8 slice 1 remediation: mandatory external-agent classification, atomic registration, purpose-bound challenges, and a corrected JWS specification (2026-11-25, M8 slice 1)

**Context:** ADR-015's first cut was independently reviewed (not by this slice's own author) before being allowed to commit. The review found real gaps: private-key-control proof was *optional* even for a would-be external agent (nothing distinguished "external" from "internal" at all); a genuine, unhandled race let two concurrent first-time key registrations for the same agent both believe they'd won; the one challenge string did double duty for two different proofs (endpoint control and key control) with no field binding either proof to its specific purpose; a pre-existing bug let a `revoked` agent be silently resurrected to `pending` by a bare re-registration, now also carrying a signing key through that same unguarded path; the JWS specification omitted the real protected-header shape (`typ: "JWT"`), never stated the literal signing-input bytes, and said nothing about Unicode escaping, NaN/Infinity, duplicate JSON keys, or RFC 8785; and the four test vectors had only ever been checked by one Python implementation, so "cross-language interoperability" was an unproven claim. This ADR records what changed to close each of those findings, and what remains explicitly open.

**Decision — agent classification is a server-held fact, never a field the registering caller can set:** `RegisterAgentIn` carries no "is this agent internal/external/legacy" field at all, and never has — that was deliberate from the first cut, but the first cut still let the signing key itself be entirely optional regardless, which amounted to the same hole by a different door. The fix is a new, operator-only `registry_organization_policies` table (`RegistryOrganizationPolicyRecord`) and a new `POST /organizations/{id}/classification` endpoint, authenticated by `registry_admin_token` — a secret distinct from, and never derivable from, `service_credential_signing_secret` (the secret every organization's own `manage_agents` credential is minted from). No organization's own credential, however scoped, can call this endpoint; `test_external_classification_cannot_be_set_by_the_registering_caller` proves a `manage_agents` bearer gets 401/403 against it. An organization absent from this table is "legacy" (the M0-M7 default, endpoint-control-only verification, unchanged) exactly as before; one present with `requires_key_proof=True` is "external," and `register_agent` now rejects (400) any registration from that organization that omits `signing_public_key_jwk` — the key stops being merely "available to opt into" and becomes mandatory at the registration call itself, not just "required once you happen to supply one" at confirm time as in the first cut.

**Decision — this is an interim, operator-driven control, not the registry-authentication replacement ADR-015 deferred, and it does not change the underlying trust boundary:** every registering organization's own calls are still authenticated by the one shared `service_credential_signing_secret`-derived HMAC credential reviewed in the "Registry authentication boundary" section below. Flagging an organization "external" via the admin endpoint does not, by itself, make it safe to let an *untrusted* outside party drive that organization's registration calls — see that section's conclusion.

**Decision — JWK validation at the boundary, not just at signature-verification time:** `message_integrity.keys.validate_ed25519_public_jwk` rejects a wrong `kty`/`crv`, a missing/malformed `x`, private-key material (a `d` member), and anything that doesn't decode to exactly 32 bytes forming a valid Ed25519 point — called on every `signing_public_key_jwk` registry-api receives, before any challenge is ever bound to it. `test_malformed_and_private_jwk_material_rejected` covers all four cases with a 400.

**Decision — key reuse across different `agent_id`s is explicitly disallowed, as a hygiene measure, not the primary security boundary:** the same encoded JWK being registered for a second, different `agent_id` is rejected (409) to avoid ambiguous key-to-identity mapping during audit/incident response. This check is a plain `SELECT` against the current table state and is *not* race-safe the way the key-substitution guard below is — a successful race here means two agents briefly share a key hint, which is an audit-hygiene annoyance, not an identity hijack, so the weaker guarantee was judged acceptable rather than worth a second CAS. `test_duplicate_key_registration_across_agents_rejected` covers the straightforward case.

### Lifecycle transition table

The previously-undocumented behavior is now both documented and enforced in one place (`_ALLOWED_TRANSITIONS` in `app.py`):

| From \ Action | `POST /agents` (re-register) | `verification/start` | `verification/confirm` | `/suspend` | `/reactivate` | `/revoke` |
|---|---|---|---|---|---|---|
| **pending** | stays `pending`; updates metadata; invalidates outstanding challenges if the card URL or key-establishment state changed | allowed | allowed (→ `active` on success) | allowed (→ `suspended`) | **rejected (409)** — pending must go through verification, not reactivation | allowed (→ `revoked`) |
| **active** | same-data retry: idempotent no-op, status unchanged (no downgrade); card-URL change: → `pending` (re-verification genuinely required) | **rejected (409)** — only a `pending` agent starts a new challenge | **rejected (409)** — nothing to confirm | allowed (→ `suspended`) | **rejected (409)** — already active | allowed (→ `revoked`) |
| **suspended** | metadata updates allowed; status **never** moves to `pending` or `active` via registration | **rejected (409)** | **rejected (409)** | allowed, no-op | allowed (→ `active`) — the *only* sanctioned path back | allowed (→ `revoked`) |
| **revoked** | **rejected (409)** — no resurrection via re-registration (closes the pre-existing bug ADR-015 did not know about) | **rejected (409)** | **rejected (409)** | **rejected (409)** | **rejected (409)** | **rejected (409)** — terminal |

Administrative reinstatement of a `revoked` agent, and a real key-rotation flow, remain separate, not-yet-built operations by design — nothing in this table creates an undocumented path to either.

**Decision — idempotency without downgrade:** a re-registration is compared against the stored record's card URL, display name, fingerprint, and key-establishment state. A byte-identical retry is a true no-op (status, `last_verified_at`, and challenges are left alone) — `test_reregistering_active_agent_with_same_data_does_not_downgrade` proves an `active` agent survives an identical re-POST without reverting to `pending`. A real card-URL change on an `active` agent *does* reset it to `pending`, deliberately — that is re-verification being correctly required for an endpoint that actually moved, not a downgrade bug — `test_reregistering_active_agent_with_new_card_url_requires_reverification` proves this is intentional and distinct from the no-op case.

### Atomic registration and challenge consumption

**Decision — first-key establishment and challenge consumption are both closed with a conditional `UPDATE`, not an unlocked read-then-write:** `do not assume a unique constraint on the public-key column solves the overwrite race` was the review's explicit instruction, and no such constraint exists. Instead:

- First-time key establishment issues `UPDATE registry_agents SET signing_public_key_jwk = :new WHERE agent_id = :id AND signing_public_key_jwk IS NULL`, checks the driver's reported row count, and treats anything other than exactly `1` as a lost race (409, retry) — never a silent overwrite. `test_concurrent_first_key_registration_only_one_wins` exercises two concurrent registrations with different keys and asserts exactly one succeeds.
- Challenge consumption issues `UPDATE registry_agents SET status='active', ... WHERE agent_id = :id AND status='pending' AND endpoint_challenge = :value`, with the same rowcount check — a second, concurrent confirm (even one that independently passed its own signature/endpoint checks) finds rowcount `0` once the first has committed and is rejected, never double-activating or re-consuming a challenge. `test_concurrent_confirm_only_one_activates` exercises this directly.
- A brand-new agent's very first registration race (two concurrent `INSERT`s for the same never-before-seen `agent_id`) is closed by the primary key itself — a losing `INSERT` raises `IntegrityError`, caught and turned into a deterministic 409, not an unhandled 500.

**A real caveat, stated rather than hidden:** the Core-level conditional `UPDATE` bypasses SQLAlchemy's ORM identity map, so the already-loaded in-memory record object is stale immediately after it commits. The first implementation of this fix re-fetched the record with `session.get(...)` expecting a fresh read — but `session.get` returns the *same* cached, stale object for a primary key already in the session's identity map; it does not re-query the database. This was caught by the registry-api test suite itself (every test asserting the post-confirm/post-registration response body failed) before being fixed by explicitly setting the known-correct values on the in-memory object after a successful CAS, instead of re-fetching. Recorded here because it is exactly the kind of correctness bug that is easy to reintroduce if this code is touched again without this context.

**Decision — key reuse across agents, stated explicitly per the review's instruction:** see the dedicated paragraph above — disallowed, as a non-race-safe hygiene check, not the identity-hijack boundary (that boundary is the race-safe CAS).

### Cryptographic challenge binding

**Decision — two separate, structured, purpose-bound challenges, never one shared string:** `verification/start` now mints `endpoint_challenge` and (only when a key is on file) `key_challenge` independently, each a canonical JSON object (`_build_challenge`) carrying `purpose` (`"endpoint-control"` or `"key-control"`), `protocol_version`, `organization_id`, `agent_id`, the registered key's RFC 7638 thumbprint (`message_integrity.keys.jwk_thumbprint`), a fresh `request_id` and `nonce`, `issued_at`/`expires_at`, and a fixed `audience`. `confirm_verification` re-parses whichever challenge it is about to rely on (`_parse_and_validate_challenge`) and confirms its bound fields actually match the current request context before ever checking the signature or the fetched endpoint value — binding by inclusion-and-re-validation, not by trusting an opaque string comparison alone. `test_endpoint_proof_cannot_be_used_as_key_proof_and_vice_versa` proves signing the wrong one of the pair, or serving the wrong one at the well-known path, is rejected even though each individual proof would otherwise be well-formed.

**Decision — a changed registration invalidates its outstanding challenges:** re-registering with a genuinely different card URL, or establishing a key for the first time, now nulls both `endpoint_challenge` and `key_challenge` rather than leaving a challenge bound to stale context outstanding. `test_challenge_replayed_after_registration_change_is_invalidated` proves a challenge issued before a card-URL change cannot be replayed after it. `test_expired_challenge_rejected` separately proves the existing TTL enforcement survived the challenge-splitting refactor intact.

### Registry authentication boundary (reviewed and documented, not rebuilt)

As instructed, this section is a conclusion, not a rewrite. `require_org_bearer` authenticates every organization-scoped call with a credential verified against `service_credential_signing_secret` — a single shared HMAC secret. Tracing it:

- **Who holds the shared secret:** `network-api` (which mints credentials) and `registry-api` (which verifies them) both hold it, configured identically by the deploying operator. No organization is ever handed this secret directly.
- **Who can issue organization-scoped credentials:** whoever can call `network-api`'s credential-issuing path with a given `organization_id` — `network-api`'s own authorization for that call is out of this slice's scope to re-audit, but registry-api's trust in the *result* is total: **registry-api performs no independent check that the organization named in a verified credential is the organization that credential was actually meant for.** It trusts the claim once the HMAC verifies.
- **Can a credential holder manufacture credentials for another organization?** Not by forging the HMAC (that requires the shared secret), but **registry-api has no mechanism of its own to detect a credential minted correctly by `network-api` for the wrong `organization_id`** — that would be a `network-api`-side bug or compromise, invisible to registry-api by construction, since registry-api's only check is "does this organization_id match the claim," never "should this caller be allowed to claim this organization_id at all."
- **Does registry-api independently validate organization ownership?** No — confirmed, not assumed. This is unchanged by this slice and was unchanged by ADR-015.

**Conclusion, stated as a mandatory release gate, not an optional improvement:** external organizations must never receive `service_credential_signing_secret` or any credential derived from it directly — every legitimate call must continue to be mediated by `network-api`'s own issuance path. More importantly, **this HMAC scheme is not a sufficient authentication boundary for allowing a genuinely untrusted, independently-operated external organization to drive its own registration calls against registry-api.** The organization-classification mechanism in this ADR controls *what registry-api demands* of an external organization's agents (a signing key, proof of control) — it does nothing to strengthen *how registry-api authenticates the organization itself* placing those registration calls. Both are needed before real external onboarding is safe; only the first exists after this slice. **Until a stronger registry-authentication mechanism replaces this shared-HMAC scheme, external onboarding is a documented, blocking prerequisite failure, not a configuration option to enable.** `TASKS.md`'s M8 section records this as a named blocking item, not a nice-to-have.

### JWS interoperability specification, corrected

`docs/specs/jws-artifact-signatures.md` was rewritten (not just amended) to state, explicitly and byte-for-byte: that canonicalization is **not** RFC 8785 and is not attempting to be (section 2a); the actual protected header shape including the `typ: "JWT"` member the reference implementation's JWT library adds and the previous revision omitted (section 3); the literal JWS signing-input byte construction, `ASCII(base64url(header) + "." + base64url(payload))`, stated explicitly rather than left implicit (section 3a); `ensure_ascii`-equivalent Unicode escaping behavior, with lowercase `\uXXXX` for every non-ASCII codepoint including both halves of a surrogate pair (section 2d); that negative zero normalizes identically to zero (section 2e); that non-integer floats are an undefined, documented residual gap rather than a silently-guessed-at serialization (section 2e); and that duplicate JSON keys and `NaN`/`Infinity` must be rejected, with the corresponding code change (section 2f).

**Decision — harden `canonicalize()` to reject `NaN`/`Infinity` outright (`allow_nan=False`), applied identically to `message_integrity.proofs.canonicalize` and `trade_protocol.negotiation.canonicalize_terms` to keep them byte-for-byte identical as documented:** this changes no previously-valid artifact's digest, because no previously-valid artifact (per `docs/PROTOCOLS.md` rule 2 — all monetary/quantity values are decimal strings) could legitimately have contained one of these non-standard tokens in the first place; it only converts a silent, already-broken serialization into an explicit, immediate rejection. `test_nan_and_infinity_are_rejected_by_canonicalize` and `test_negative_zero_normalizes_identically_to_zero` cover this.

**Decision — duplicate-key rejection lives in a new `strict_json_loads` helper, not inside `canonicalize()` itself, because it cannot apply there:** `canonicalize()` takes an already-parsed in-memory object (a Python `dict`), which cannot contain a duplicate key by construction — the ambiguity exists only one layer earlier, when raw JSON *text* is deserialized. Nothing in this codebase currently deserializes an artifact from raw JSON text (the A2A SDK's protobuf `Struct` transport has no such concept either), so `strict_json_loads` is forward-looking infrastructure for any future raw-JSON transport, not a fix to an exploitable gap in the current one — stated plainly rather than implied to be more urgent than it is. `vector_06_duplicate_key_rejected.json` and its test exercise it directly.

**New signed test vectors:** `vector_05_unicode_content.json` (verify-success, non-ASCII payload content, proving the `\uXXXX` escaping claim against the real implementation) and `vector_06_duplicate_key_rejected.json` (a `parse_failure` vector carrying raw JSON text, not a pre-parsed object, proving `strict_json_loads` rejects it while a bare `json.loads` silently keeps the last occurrence).

### Independent cross-language verification

**Decision — a minimal Node.js harness, built from the specification document alone, with zero AIMO-package and zero npm-package dependencies:** `docs/specs/test-vectors/cross-lang-harness/` (`canonicalize.mjs`, `jws.mjs`) re-implements sections 2–4 of the spec using only Node's built-in `node:crypto`. `verify-vectors.mjs` loads and checks all six vectors against this from-scratch implementation; `generate-artifact.mjs` signs a fresh artifact entirely in Node.js, and `packages/message-integrity/tests/test_jws_vectors.py::test_node_generated_artifact_verifies_in_python` proves the Python reference implementation accepts it — both directions, not just one.

**This proves Python ↔ Node.js interoperability specifically. It does not prove interoperability with any other language or runtime.** The specification document says so explicitly, and this ADR repeats it rather than letting the claim drift into something broader than what was actually tested.

## ADR-017 — M8 slice 2 (per-agent signing authority): scoped delegation, deterministic key resolution, freshness-bounded revocation, and constrained legacy attribution (2026-11-25, M8 slice 2)

**Status: implemented on a dedicated review branch, pending PostgreSQL CI verification and review — not yet merged to main.** This ADR records the amended design after a review of the initial slice 2 proposal found it under-specified in five respects: it didn't say where delegation signing actually happens, it implied a delegation authorizes every artifact type rather than a scoped set, it didn't make key resolution collision-free, it didn't specify cache-freshness/fail-closed behavior for revocation, and it didn't constrain what the pre-existing organization-root ("legacy") signing path is allowed to satisfy once per-agent attribution exists as a concept. All five are resolved below, and implemented — see "Implementation notes" below the design/acceptance-test sections for what the code actually does, including where it deviates from or narrows the design's own test list.

**Decision — the organization signs its own delegations; `network-api` never holds or touches a private key.** The delegation token is constructed and signed entirely inside the organization's own trust boundary — the same place `buyer_signing_private_key_pem`/`supplier_signing_private_key_pem` already live today, using the same `message_integrity` signing primitives, not a new capability inside `network-api`. The finished JWS compact token is then submitted to a new authenticated endpoint, `POST /organizations/{id}/delegations`, gated by the same organization-management credential boundary that already governs `organization_signing_keys` rotation (unchanged auth model — no new externally-reachable surface, no change to who can act for an org). `network-api`'s role on receipt is purely verification and policy enforcement, never issuance: it (a) cryptographically verifies the submitted token against that organization's currently-live root JWKS, (b) checks the submitting caller's credential authorizes managing that organization, and (c) validates the structural invariants in the next section — only then does it persist and begin serving the token. If a submitted token fails any of these, nothing is stored.

**Decision — a delegation authorizes a scope, not blanket signing authority.** The signed payload carries `scope: {artifact_types: [...], protocol_version: "<trade_protocol version>"}`, in addition to identity/validity claims. A receiver verifying a business artifact must check the artifact's own declared type against `scope.artifact_types` *before* treating the signature as authorizing that action — a delegation naming only `["request_for_quote", "quote", "counterproposal", "accept_proposal", "reject_proposal"]` cannot satisfy verification for `authorization_evidence`, `order_commit_request`, or `order_confirmation`, regardless of how valid the signature itself is. This check lives in the message-authentication layer, strictly *before* OPA or the existing commitment-authorization flow (ADR-011) ever runs — a valid, in-scope delegation is proof of *who may speak*, never itself a grant to execute an order; OPA and `supplier_agent.commitment`'s mutual-authorization logic are unchanged and remain the only source of binding-action permission.

**Decision — the full signed claim set, with explicit domain separation from business artifacts.** Protected header: `{"alg": "EdDSA", "kid": "<issuing root kid>", "typ": "aimo-delegation+jws"}`. Payload: `{iss: organization_id, sub: agent_id, aud: <network/environment identifier>, jti: <unique delegation id>, iat, nbf, exp, delegated_kid, delegated_pubkey_jwk, scope: {artifact_types, protocol_version}}`. **Cross-cutting change required of the existing business-artifact proof format:** today's `sign_artifact` relies on PyJWT's default `typ: "JWT"` header (ADR-016 already documented this as a spec-accuracy gap); slice 2 additionally gives business artifacts their own explicit discriminator, `typ: "aimo-artifact+jws"`, so that a delegation token and a business-artifact proof are structurally distinguishable by header alone, not merely by which endpoint happened to serve them. A verifier checks `typ` before attempting to interpret a token's payload as either shape; feeding a delegation to `verify_artifact_proof` or a business artifact to the new delegation-verification path must both fail at this check, before any claim is even inspected — this is additive (old business-artifact signatures remain verifiable; only new signing adds the explicit `typ`) and does not change any previously-valid artifact's digest, since `typ` lives in the JWS header, never the canonicalized artifact payload itself.

**Decision — key resolution is collision-free by database constraint, not by convention (corrected after a second review pass).** `AgentSigningDelegationRecord` carries a real unique constraint on `(organization_id, delegated_kid)`. Separately, the Ed25519 public-key **thumbprint** (RFC 7638, reusing `message_integrity.keys.jwk_thumbprint` from slice 1) of a delegated key is excluded **organization-wide, across every agent in that organization** — enforced by a unique constraint scoped to `(organization_id, pubkey_thumbprint)` over the currently-**live** (unexpired, unrevoked) row subset, not a per-agent-pair check and not merely "the same two agents can't share a key." This stops the same key material being delegated to *any* two agents in the organization concurrently, while still allowing a key to be re-delegated after its original delegation has fully lapsed or been revoked (no permanent exhaustion of key material). **Multiple concurrently-live delegations for the same agent are explicitly allowed** — deliberate, not an oversight, so slice 3's controlled key rotation has an overlap window to land in rather than requiring instantaneous cutover.

**Decision — the root/delegated `kid` namespace is enforced atomically, symmetrically, in *both* write paths, not just at delegation publication.** The first draft of this ADR only checked for collision on the delegation-publication path (new delegated `kid` against existing root `kid`s); this was incomplete — the reverse race (a *new root key* being added via the existing `organization_signing_keys` rotation flow, concurrently with a delegation publication, each colliding with the other's `kid`) was unaddressed. Both write paths now participate in one shared namespace check for a given `organization_id`: each insert (root-key rotation *and* delegation publication) runs inside a transaction that takes a row-level lock scoped to that `organization_id` (e.g. `SELECT ... FOR UPDATE` against a small per-organization "kid namespace" guard row, or equivalently a single unified unique index spanning both `organization_signing_keys.kid` and `agent_signing_delegations.delegated_kid` per organization if the two can be queried through one constraint-bearing view/table) before either write commits — a losing concurrent insert on *either* side is rejected with a deterministic conflict response, never silently admitted. This mirrors slice 1's "CAS, not an unlocked read-then-write" principle, extended across two tables instead of one.

**Decision — explicit signed audience, with its meaning kept separate from the business-artifact proof's existing `aud` claim; and a versioned, backward-compatible `typ`.** The delegation's `aud` claim denotes the intended **network/environment** (e.g. `"aimo-network:production"` vs a staging equivalent) — this is a *different semantic domain* from the business-artifact proof's pre-existing `aud` (ADR-012's claim shape), which denotes the **recipient organization_id** for that specific artifact. Both are literally the JWT claim named `aud`, and a verifier must never check one against the other's expected value — delegation verification checks `aud` against the configured network/environment identifier; business-artifact verification checks it against `expected_recipient_organization_id`, exactly as today, unchanged. **`typ` compatibility is explicitly versioned, not a hard cutover:** a business-artifact proof's `typ` header is accepted as legacy-valid when it is either absent or exactly `"JWT"` (PyJWT's pre-slice-2 default, per ADR-016) — these verify exactly as before, with `attribution` and audit logging recording `typ_version: "legacy"`. A `typ` of exactly `"aimo-artifact+jws"` is the new, explicit discriminator, recorded as `typ_version: "v1"`. Any other `typ` value (and, specifically, `"aimo-delegation+jws"` presented where a business artifact was expected, or vice versa) is rejected outright. No previously-valid artifact's acceptance changes under this scheme — only an intentionally mislabeled or cross-purpose token is newly rejected.

**Decision — revocation is only as fast as the freshest check a receiver is willing to make, and this must be specified, not assumed.** A `JwksResolver`-equivalent for delegations caches for a bounded TTL (reusing the existing 300-second default is the starting point, revisited if slice 2's threat model demands tighter). **Fail-closed, stated explicitly:** a cache entry is never served past its TTL under any circumstance, including a failed refresh — a refresh failure on an expired entry is treated identically to "key/delegation not found," i.e. rejection, never "use the last-known-good value because the network is having a bad day." **Sensitive artifact types bypass the cache entirely:** `authorization_evidence`, `order_commit_request`, and `order_confirmation` force a fresh, uncached fetch of both the delegation record and the registry-api agent-status check on every verification — the 300-second window is acceptable for negotiation-phase artifacts, not for anything commitment-adjacent. **No fallback between verification paths:** which path a `kid` resolves through (organization-root or per-agent-delegated) is structural, determined by which keyspace the `kid` belongs to — not a best-effort "try delegated, then try legacy if that fails." A delegated-path failure (lookup failure, malformed response, expired/revoked, scope mismatch) is a rejection, full stop; it never falls through to re-attempt verification as if the artifact had been root-signed. **`revoked_at` lives outside the signed claims, as mutable `network-api`-held metadata** on the stored record — identical in spirit to how `OrganizationSigningKeyRecord.revoked_at` already works — never inside the immutable JWS payload itself, since revocation is a fact the network operator asserts *about* a signed statement, not a fact the statement asserts about itself.

**Decision — the legacy root-signing path is preserved for backward compatibility but explicitly cannot satisfy a per-agent-authority requirement.** A root-signed artifact proves organization-level authority only — it says nothing about which agent, or which private key, actually produced the signature, because by construction the whole organization shares that one key. `VerifiedProof` gains an explicit `attribution: Literal["organization", "delegated_agent"]` field, set structurally by which verification path succeeded, surfaced to both audit logging and to OPA as an input (so a policy *can* require `attribution == "delegated_agent"` for a given organization/relationship/artifact-type combination without that check being hardcoded into the message-authentication layer alone). A root-signed artifact presented where such a policy applies is rejected — the legacy path's continued existence for backward compatibility must never become a way to route around slice 2's stronger attribution simply by omitting a delegation.

### Implementation notes (2026-11-25) — status updated from "design approved" to "implemented, pending review"

**Decision — the kid-namespace guard is a shared unique-constraint table, not a row lock.** Rather than `SELECT ... FOR UPDATE` against a guard row, `OrganizationKidNamespaceRecord` (`organization_kid_namespace`, composite primary key `(organization_id, kid)`) is a pure namespace-reservation table with no key material of its own. Both `register_signing_key` (root-key rotation) and `publish_delegation` (new) insert one row here, in the *same transaction* as their own table's insert, before either commits. The composite primary key itself is the atomic check — a losing concurrent insert on either side raises `IntegrityError`, caught and turned into a deterministic `409`. This is simpler than a lock-then-check-then-write sequence (nothing to get the ordering of wrong) and is symmetric by construction: it does not matter which endpoint's code runs the insert, the same constraint governs both. `register_signing_key` was also given a `try/except IntegrityError` it previously lacked — a welcome, small hardening of a pre-existing, previously-not-fully-race-safe path, not scope creep.

**Decision — the organization-wide live-thumbprint exclusion is a partial unique index**, `uq_org_live_pubkey_thumbprint` on `(organization_id, pubkey_thumbprint) WHERE revoked_at IS NULL`, created identically via SQLAlchemy's `Index(..., postgresql_where=..., sqlite_where=...)` (so `Base.metadata.create_all`-based tests and real Alembic migrations stay consistent) and via raw SQL in migration `0005`. "Live" is defined here as *not revoked* — not also "not yet expired" — because a static partial-index predicate cannot reference the current time; an operator who wants to free up reuse of an about-to-expire key's thumbprint before its `not_after` passes must explicitly revoke it first. This is a real, small gap between the index's literal behavior and ADR-017's "(unexpired, unrevoked)" phrasing, recorded here rather than silently left to be discovered later: an expired-but-not-yet-revoked delegation's thumbprint still occupies the unique slot.

**Decision — `(organization_id, delegated_kid)` uniqueness is permanent, not scoped to live rows**, and this is what makes revoke-then-republish-of-the-identical-token safe without any extra bookkeeping: the original (now-revoked) row still occupies that slot, so resubmitting the same token hits the ordinary duplicate-kid rejection. Confirmed by `test_revoke_then_republish_identical_token_cannot_resurrect_it`.

**Decision — `expected_audience=None` is a legitimate mode of `verify_delegation_token`**, used only by `network-api`'s own publish-time verification (which has no prior expectation of what audience a submitted delegation should carry — only the eventual *receiver* does) — it verifies the signature and every other claim, accepting whatever `aud` the token itself declares. Every receiver-side call (the orchestrator, the HTTP delegation resolver) always passes its own configured `network_audience` explicitly; this mode is never reachable from a verification path a receiving agent relies on.

**Decision — revocation freshness bound, exactly as implemented:** `HttpJwksResolver`/`HttpDelegationResolver` share one `cache_ttl_seconds` default (300s, unchanged from M5.1/ADR-012 — not tightened, since nothing in this slice's threat model demanded it). Both resolvers are fail-closed by construction: a cache entry already past its TTL is never returned; the only path to a result past that point is a fresh fetch, and a fetch that fails raises, it does not fall back to the stale entry (`jwks.py`'s `get_key`/`delegation_resolver.py`'s `get_delegation`, both audited for this property — the stale `entry` variable is simply never read again after a failed refresh attempt). `verify_artifact_proof_with_delegation` sets `force_fresh=True` automatically whenever the artifact's own (unverified) `typ` claim is in `COMMITMENT_ADJACENT_ARTIFACT_TYPES = {"authorization_evidence", "order_commit_request", "order_confirmation"}` — bypassing the cache entirely for both the root/delegation key lookup and (by the caller, in `buyer_agent`/`supplier_agent`'s `message_auth.py`) the registry-api agent-status check, which was already an uncached, real-time HTTP call on every verification and needed no change.

**Decision — "no fallback between paths" is structural, not merely documented:** `verify_artifact_proof_with_delegation` probes the organization's root JWKS first; only a clean `KeyNotFoundError` (the kid simply isn't a root key) causes it to consult the delegation resolver. Any other failure from the root-key lookup (a fetch error, for instance) is a terminal rejection — it is never interpreted as "try the delegation path instead." Once a candidate key (root or delegated) is actually found, the resulting verification (signature, digest, scope, agent-id match) is final; a failure there is never retried against the other keyspace. `test_delegation_lookup_failure_has_no_fallback_to_legacy_path` exercises the one case that could plausibly be confused for a missing fallback (a kid that resolves to neither keyspace).

**Decision — the legacy-`typ` acceptance window is exactly `{None, "JWT"}`**, matching PyJWT's actual pre-slice-2 default header shape (confirmed directly, not assumed — see ADR-016's own prior finding that PyJWT adds `typ: "JWT"` even though earlier code never asked it to). `sign_artifact` now always sets `typ: "aimo-artifact+jws"` going forward; every pre-existing signed artifact (including every one of slices 0–1's committed test vectors) still verifies, recorded as `typ_version="legacy"`. `test_pre_slice2_signed_artifact_verifies_as_legacy_typ` constructs a token exactly the old way (bypassing `sign_artifact` to avoid the new header) and confirms this directly, rather than merely trusting that old vectors still pass.

**Deviation from the original test list, stated honestly rather than overclaimed:**
- Test 17 is split into two concrete tests — `test_delegated_kid_colliding_with_root_kid_rejected` and `test_cross_agent_thumbprint_reuse_rejected_sequentially` — plus two Postgres-backed concurrent variants (`test_concurrent_delegated_kid_publication_only_one_wins`, `test_concurrent_cross_agent_thumbprint_reuse_only_one_wins`) and one symmetric-namespace concurrency test (`test_concurrent_root_kid_rotation_vs_delegation_publication_root_wins`). The last of these races two concurrent HTTP calls via `asyncio.gather` and asserts the outcome is `{200, 409}` regardless of which side wins — it genuinely exercises the shared-constraint guard under concurrency, but because `asyncio.gather`'s scheduling order isn't pinned, a *single* run exercises only whichever direction the event loop happens to schedule first; it does not deterministically prove both "root wins" and "delegation wins" orderings within one invocation. ## ADR-018 — M8 slice 3 design (key lifecycle and historical evidence): independent evidence findings, a bound evidence receipt, an append-only ledger, a corrected revocation bound, and a thumbprint reservation separate from revocation (2026-11-26, M8 slice 3)

**Status: implemented on review branch `m8-slice3-review`, pending CI/merge review.** Sections 1-5 and the acceptance-test list below are the approved design, amended once before implementation per the review that follows this status line. The "Implementation notes" section at the end of this ADR records exactly how the four additional invariants (A-D) given alongside implementation approval were built, corrects a wording error from the design phase, and states remaining limitations plainly.

**Status (design phase, superseded by the line above once implementation began): design under review; amended once already, implementation not started.** The first draft of this ADR proposed a three-way "currently valid / valid-at-observed-time / valid-at-claimed-time-only" classification for historical evidence. Review found this claims more than the evidence supports: "currently valid" and "valid at an observed past time" are not mutually exclusive categories, and neither, by itself, establishes that a business action was authorized — scope, audience, registry status, trading relationship, policy and approval are all independent facts that can each be established, contradicted, or simply unavailable, and blending them into one verdict hides exactly the distinction this slice exists to preserve. This revision replaces the three-way classification with an itemized evidence report, tightens what the existing replay-defense records actually prove (verified insufficient by inspection, not assumed), replaces "convert expiry into revocation" with a separate reservation concept, and corrects a wrong revocation-bound statement from the first draft.

### 1. Historical evidence report — independent findings, never a blended verdict

A request to assess a past artifact returns a structured report with the following fields, each established independently; the report is additive evidence, not a single pass/fail:

```
HistoricalEvidenceReport:
  signature_verification: "valid" | "invalid"
    # Checked FIRST, independent of any timestamp claim. If "invalid",
    # every other field is reported as "not_applicable" — an invalid
    # signature is invalid regardless of what any timestamp says.

  key_or_delegation_status:
    at_signer_claimed_time:      # using the artifact's own iat — see §2's trust limit
      status: "active" | "expired" | "revoked" | "unknown"
      scope_check: "in_scope" | "out_of_scope" | "not_applicable"
      audience_check: "match" | "mismatch" | "not_applicable"
    at_receiver_observed_time:   # using an evidence receipt, if one exists — see §2
      status: "active" | "expired" | "revoked" | "unknown"
      scope_check: "in_scope" | "out_of_scope" | "not_applicable"
      audience_check: "match" | "mismatch" | "not_applicable"

  time_evidence:
    signer_asserted_iat: <value or null>       # always labeled signer-asserted
    receiver_observed_at: <value or "unavailable">
    anchor_used: "receiver_observation" | "signer_claim_only" | "none"

  historical_context_evidence:    # each independently "established" | "contradicted" | "unavailable"
    registry_status_at_time: ...
    trading_relationship_at_time: ...
    policy_version_at_time: ...
    approval_evidence_at_time: ...

  current_authorization_status:   # only populated if explicitly requested; kept structurally
    key_or_delegation_currently_valid: "yes" | "no"   # separate from the historical fields above
```

**Hard rules, stated because the first draft didn't enforce them structurally:** an invalid signature is reported invalid regardless of any timestamp evidence. A report whose `anchor_used` is `"signer_claim_only"` must never be rendered or summarized in a way that implies independent corroboration of when signing occurred — any caller-facing summary of such a report is required to carry the phrase "signer-asserted time only, not independently corroborated" verbatim, not a softened paraphrase. `current_authorization_status` (Q1) is structurally a separate block from the historical fields (Q2) — never merged into one "is this valid" field, so a reader cannot mistake "valid now" for "was valid then," or vice versa.

### 2. Binding `seen_at` to the exact evidence, with its trust limit stated

**Verified, not assumed:** `BuyerSeenMessageProofRecord`/`SupplierSeenMessageProofRecord` (M5.1) carry only `jti`, `negotiation_id`, `artifact_type`, `organization_id`, `agent_id`, `seen_at` — read in full for this ADR. They do **not** carry the artifact's own content digest, the `kid`/`delegated_kid` actually used to verify it, a delegation `jti` when the delegated path was used, or an explicit verification outcome (a row's mere existence implies "accepted"; a rejected artifact leaves no row at all today). **This is insufficient for evidentiary use as specified** — a dispute needs "this exact artifact, verified against this exact key, at this exact observed time," and today's row only supports "a message with this jti from this agent was seen."

**New: a `VerificationEvidenceReceiptRecord`**, additive (existing replay-defense tables and their jti-uniqueness behavior are unchanged — this is a new, parallel record, not a replacement): `{receipt_id, jti, artifact_digest, kid_used, delegated_kid (nullable), delegation_jti (nullable), organization_id, agent_id, scope_checked: {artifact_type, protocol_version}, verification_outcome: "accepted" | "rejected", rejection_reason (nullable), observed_at}`. `observed_at` is assigned by the receiving service's own clock at the moment of verification — never client-supplied, never backdated. Rejections are recorded too (not just acceptances), since a dispute may turn on "was this rejected for a reason that later became moot."

**Trust limit, stated explicitly and permanently attached to every use of this data:** a `VerificationEvidenceReceiptRecord` is an assertion by the *receiving organization's own system*, not an independently witnessed fact. Its `observed_at` is a database timestamp, subject to: that system's own clock accuracy/drift; the theoretical possibility of later modification by someone with sufficient database access (mitigated, not eliminated, by §3's append-only-permissions policy); and the theoretical possibility of collusion between the receiver and whichever party benefits from the receipt. **Category naming never claims this is "proof of when signing occurred"** — every surfaced label is "receiver-observed verification time," paired with this limitation, not a bare timestamp presented as fact.

### 3. The ledger is an event history from a trusted operator, not a retroactive source of certainty

The key-event ledger (§4 of the original draft, retained) is amended:

- **Retains the exact key material and signed tokens, not just status flags** — every root-key JWK and every delegation's full JWS compact token, permanently, so a historical artifact can actually be *re-verified* cryptographically against period-correct key material, not merely have its status looked up.
- **Two timestamps per event, not one:** `effective_time` (when the event semantically took effect — for a revocation, the moment an operator chose it to apply, essentially "now" at revoke time; for an expiry, the key/delegation's own `not_after`) and `recorded_at` (when `network-api`'s own process appended the ledger row — which can legitimately be later than `effective_time`, e.g. a cleanup job noticing an expiry after the fact; **expiry is effective at `not_after` regardless of when any job gets around to recording it**).
- **Atomic with the lifecycle mutation it describes:** the `UPDATE` that sets `revoked_at` (or any other lifecycle field) and the ledger `INSERT` recording that event happen in the same database transaction — committed together or not at all, never one without the other.
- **Append-only, access-controlled, retained on a stated policy:** no code path updates or deletes a ledger row once written (enforced at the application layer pending any stronger DB-role-level grant restriction, which is a deployment hardening step this slice names but does not itself implement); reading historical evidence requires the same organization-management credential boundary already used elsewhere, *plus* its own access log — who queried which organization's historical evidence, and when, since the sensitivity of historical evidence justifies knowing who has been looking at it. Retention defaults to indefinite, operator-configurable down to a stated minimum (reconstructed recommendation: 7 years, matching a typical commercial-dispute limitations period) — named as an explicit policy choice, not an accident of either "kept forever by default" or "silently pruned."
- **Pre-slice-3 rows get a labeled migration snapshot, never a fabricated history.** Every `OrganizationSigningKeyRecord`/`AgentSigningDelegationRecord` row that predates this ledger's existence receives exactly one `migration_snapshot` event at migration time, explicitly labeled as reconstructed *current* state — **no synthetic "issued" or "revoked" event with a backdated timestamp is ever invented** for anything that happened before this ledger existed. A pre-slice-3 row that was already revoked gets a `migration_snapshot` noting its current `revoked_at` value as observed, not a historical revocation event asserted to have been ledger-recorded at that time.
- **Named, permanent limitation:** this ledger is a record kept by a trusted platform operator (`network-api`'s operator). It is not a tamper-proof external timestamping authority (not an RFC 3161 TSA, not a blockchain anchor) — evidence drawn from it is only as trustworthy as trust in that operator running the system honestly. This slice does not solve that; it states it.

### 4. Revocation bound, corrected

The first draft said a revocation is "guaranteed visible within `cache_ttl_seconds` plus one failed-refresh retry interval" — **this was wrong, and is retracted.** A retry interval during which a revoked key could still authorize is exactly the stale-use-after-expiry case slice 2 already built fail-closed behavior to prevent. **Corrected bound: the maximum stale-acceptance window is `cache_ttl_seconds` itself, full stop.** A cached entry may be used up to (not beyond) its TTL. The instant the TTL is reached, the next verification attempt **must** force a fresh fetch; if that fetch fails, verification is denied — there is no additional grace or retry window in which a stale value is still trusted, exactly matching the already-correct behavior slice 2 implemented and tested (the error was in this ADR's prose, not in the code).

This bound is itself conditional on two named assumptions: `network-api`'s own read-after-write consistency (a revoke committed by one process is visible to the very next read by another), and ordinary clock-sync assumptions underlying any TTL/expiry comparison — stated as assumptions, not independently re-verified by this slice.

**Residual time-of-check/time-of-use risk, named as a SEPARATE risk from the cache-TTL bound above, not something that bound closes:** the `cache_ttl_seconds` bound above governs only how stale a *cached read* may be — it says nothing about, and does not by itself bound, the separate window between a fresh check succeeding and the business action it authorized actually being finalized downstream. A freshly-passed, uncached commitment check can still race a revocation that lands immediately afterward. This is not eliminated by this design, and this slice introduces no mechanism that closes it — it is documented here, explicitly, as an accepted residual risk of any pull-based freshness model. Its exposure window happens to be small in practice (roughly the round-trip/processing time of one fresh check, not the full cache TTL), but "small" is not "bounded by a stated mechanism," and this ADR does not claim the latter.

### 5. Thumbprint reservation, kept separate from revocation; root cutover defined precisely

**The first draft's "auto-revoke an expired delegation to free its thumbprint" is withdrawn — it conflates two lifecycle meanings this design otherwise carefully keeps apart.** Instead: a new, distinct field, `thumbprint_reservation_released_at: datetime | None`, separate from `revoked_at`. The organization-wide live-thumbprint partial unique index is redefined to be scoped to rows where `thumbprint_reservation_released_at IS NULL`, not `revoked_at IS NULL`. A scheduled/operator-triggered job, after a delegation's `not_after` plus a configured grace period, performs a transactional `UPDATE` setting only `thumbprint_reservation_released_at = now()` — `revoked_at` stays `NULL` for a delegation that simply expired; the ledger records this as its own event type, `reservation_released`, never mislabeled `revoked`. An operator may still explicitly revoke a delegation for cause, independent of whatever the reservation-release job is doing — the two fields, and the two ledger event types, never collapse into each other. **Fail-safe direction preserved exactly as specified:** if the release job fails or is delayed, `thumbprint_reservation_released_at` stays `NULL` and the slot remains held — the system never silently frees a reservation.

**Root cutover, defined precisely, as requested:**
- An incoming root key (`status="rotating"`) may issue new delegations starting at its own `not_before` — delegation publication validates the issuing root's status is in `("active", "rotating")` and `not_before <= now`, exactly as signature-verification already does.
- The outgoing root key continues to be usable for issuing *new* delegations until an operator explicitly stops it (moving it out of `active`/`rotating`) — cutover is an explicit operator action, not automatic the moment a replacement key exists; both keys may legitimately issue concurrently during the overlap window.
- **The precise consequence when an issuing root expires or is revoked while delegations it issued are still within their own `not_after`:** such a delegation becomes **unusable for any new verification** the moment its issuing root goes dark — not because the delegation itself expired, but because step one of the two-hop chain (verifying the delegation's own signature against its issuing root's live key) can no longer succeed once that root key is absent from the live JWKS. The delegation's own `not_after` becomes irrelevant to Q1 the moment its issuing root is gone. **This is named here as a required operational step, not something this slice automates:** retiring a root key requires first re-issuing (re-signing, under the new root) any still-live delegations that were issued under it, or deliberately accepting that they go dead early. This belongs in the root-rotation runbook.

### Acceptance tests (amended; supersedes the original 9-test list)

1. Signature-invalid artifact reports `signature_verification: "invalid"` and every other field `"not_applicable"`, regardless of any timestamp claim presented alongside it.
2. A report with `anchor_used: "signer_claim_only"` never renders or is summarized as independently corroborated — assert the exact required caveat string is present wherever such a report is surfaced.
3. `VerificationEvidenceReceiptRecord` correctly binds `artifact_digest`, `kid_used`/`delegated_kid`, and `verification_outcome` for both an accepted and a rejected verification attempt.
4. A backdated `iat` (claimed before an actual revocation, but with no corresponding evidence receipt) is never promoted to `anchor_used: "receiver_observation"` — it remains `"signer_claim_only"`, correctly limited.
5. Ledger append and the lifecycle `UPDATE` it describes commit atomically — a forced failure after the lifecycle `UPDATE` but before the ledger `INSERT` (or vice versa) leaves neither committed.
6. Migration produces exactly one `migration_snapshot` event per pre-existing row, with no fabricated `issued`/`revoked` event at any backdated time.
7. Cache entry is honored up to and including its TTL boundary; the very next check past TTL, if the refresh fails, denies authorization — no retry-window grace period during which a revoked key still authorizes.
8. Reservation-release job unblocks a thumbprint via `thumbprint_reservation_released_at`, leaving `revoked_at` untouched and recording a `reservation_released` ledger event distinct from `revoked`.
9. Reservation-release job failure/delay leaves the slot held — a concurrent attempt to delegate the same key material to a different agent is still rejected.
10. A delegation still within its own `not_after` fails live verification once its issuing root key is revoked/expired — proving the "root cutover kills still-unexpired delegations" consequence is real, not just documented.
11. Genuinely interleaved-transaction PostgreSQL tests for the namespace guard, both orderings (carried over from the original plan, unchanged).
12. Historical-evidence code paths are structurally unreachable from, and never consulted by, the live Q1 verification path (import-boundary/structural test, not just behavioral).

Global-admin credential and the shared-HMAC registry-authentication boundary (ADR-015/016) — untouched, still closed, not widened by any lifecycle or historical-evidence feature in this slice.

### Implementation notes (added once slice 3 was actually built, on review branch `m8-slice3-review`)

Implementation proceeded under four additional invariants given alongside approval, plus one wording correction — recorded here exactly as built, not merely as specified.

**Invariant A (receipt binding) as implemented:** `message_integrity.evidence.EvidenceReceipt` binds to the artifact's own pre-existing `artifact_digest` claim (now exposed as a field on `VerifiedProof` itself, populated by the same internal check `verify_artifact_proof_with_known_key` already performed) rather than re-hashing the raw wire representation separately — this is a deliberate simplification from the original invariant's literal wording, justified as follows: because SHA-256 is one-way, binding to *any* correct digest of the content (including one that was already being computed anyway) makes a stored receipt unable to leak a bearer credential the artifact's payload might carry (ADR-011), regardless of whether that digest is freshly computed or reused — the one-wayness is what satisfies "never retain bearer credentials," not which exact digest-computation call site produced it. A rejected verification's `claimed_kid`/`claimed_artifact_digest` are read via the same best-effort, never-raising `jwt.get_unverified_header`/`jwt.decode(verify_signature=False)` pattern this codebase already uses elsewhere (`parse_unverified_proof`), and are stored in fields structurally distinct from the trusted `kid_used`/`artifact_digest` — proven by `test_rejection_receipt_uses_claimed_fields_never_trusted_fields` and `test_rejected_verification_records_a_claimed_only_receipt`.

**Correction, from the slice 3 merge review — disclosed explicitly rather than left implicit:** `artifact_digest` (`proofs._artifact_digest`, a SHA-256 over the canonicalized artifact with its `proof` field removed) is a property of the artifact's **content only** — it does not, and structurally cannot, depend on which key or `kid` actually signed that content. **Two different valid signatures over identical artifact content (two different delegated keys, or a root key versus a delegated key) produce the identical `artifact_digest`.** The digest alone therefore cannot distinguish "which proof was checked" from "which content was checked" — this is exactly the gap the review raised, and it is real, not a misunderstanding to correct away. It is `kid_used`/`delegated_kid`, not the digest, that identifies which signature was actually verified; **it is the combination of both fields, never the digest by itself, that disambiguates a substituted proof** (identical content, re-signed by a different, equally-valid key) from a genuinely identical, re-sent proof. `evidence.py`'s module docstring now states this explicitly, and `test_altered_content_with_otherwise_identical_signing_produces_a_different_digest` / `test_substituted_proof_over_identical_content_shares_a_digest_but_differs_in_kid_used` (added on the review branch) prove both halves directly: the digest alone distinguishes different content under the same key, but is identical for different keys over the same content — only `kid_used` catches that second case.

**Invariant B (reservation release) as implemented:** migration `0006` drops and recreates `uq_org_live_pubkey_thumbprint` with `WHERE revoked_at IS NULL AND thumbprint_reservation_released_at IS NULL` (both conditions, not one replacing the other — a row stops blocking reuse when EITHER is true, since revocation already correctly freed the slot before this slice and must keep doing so). Backfill sets no value for the new column (its default is `NULL`, asserted explicitly in the migration rather than left to accident). `POST .../delegations/{jti}/release-reservation` fails closed (409) before the grace period elapses, is idempotent once released, and never touches `revoked_at`. Tested: a forced-rollback test proves the release-plus-ledger-event transaction is all-or-nothing (`test_forced_rollback_leaves_reservation_held_not_half_released`); a same-thumbprint release-vs-publish race is tested via `asyncio.gather` and asserts the invariant that at most one live row for that thumbprint can ever exist, rather than asserting a fixed winner (`test_concurrent_release_and_new_publication_never_both_succeed_live`) — this is a probabilistic-ordering test, like slice 2's original namespace race test, not a deterministically-interleaved one (see remaining limitations below).

**Invariant C (historical uncertainty) as implemented:** `evaluate_historical_evidence`'s `_status_at` helper explicitly computes the earliest *real* (non-`migration_snapshot`) ledger fact's `effective_time` and reports `"unknown"` for any requested time before it — a `migration_snapshot` can never be used to answer a question about a time earlier than its own `recorded_at`, proven by `test_migration_snapshot_cannot_establish_status_before_its_own_recorded_time`. A backdated signer-claimed `iat` with no corroborating receipt stays `anchor_used="signer_claim_only"` permanently — `test_backdated_iat_with_no_receipt_is_not_corroborated` proves this is never silently upgraded.

**Invariant D (root cutover) as implemented, and a real bug found in the process:** the root-cutover behavior was expected to "fall out of" `HttpDelegationResolver._fetch`'s existing `except DelegationError: continue` handling (its own docstring already claimed this). Writing the actual test (`test_delegation_stops_authorizing_once_cache_expires_past_root_revocation`) found this claim was **false**: a dead issuing root key surfaces from `verify_delegation_token` as `InvalidSignatureError` (raised when the root-key JWKS lookup itself fails), which is a `ProofError` *sibling* of `DelegationError`, not a subclass of it — so `_fetch` did not catch it, and a root-cutover crashed the whole delegation-list fetch instead of correctly making just that one delegation disappear while others remained usable. Fixed by widening the catch to `ProofError` (the actual common base), with the reasoning for the widened catch documented inline at the fix site. This is exactly the kind of gap invariant D was added to catch rather than assume — recorded here so the fix's motivation isn't lost. Both the cache-boundary and commitment-adjacent (zero-TTL-grace) cases are now covered.

**Wording correction applied:** the "Residual time-of-check/time-of-use risk" paragraph in section 4 above has been rewritten to state plainly that the `cache_ttl_seconds` bound governs cached-read staleness only and does not, by itself, bound the separate check-to-commit race — that race is named as a distinct, unsolved residual risk, not implied to be covered by the TTL mechanism. No new mechanism was introduced to close it, per the instruction not to invent one that doesn't fall out naturally from the rest of this slice's design.

**Test evidence:** new test files `packages/message-integrity/tests/{test_evidence,test_historical_evidence,test_historical_evidence_structural_separation,test_root_cutover}.py`; `apps/network-api/tests/{test_key_lifecycle_ledger,test_migration_0006_snapshot_backfill}.py`; `apps/buyer-agent/tests/test_message_auth_evidence.py`. ### Merge-review findings and fixes (added on `m8-slice3-review`, before merge)

**1. Deterministic concurrency — CONFIRMED GAP, now closed.** The `asyncio.gather`-based tests above, and the "deterministic" tests added during PR #3's own merge-readiness review (`test_delegations_merge_review.py`), were checked directly: the latter are purely **sequential** (one `await` fully completes before the next begins), not concurrent at all, and the former cannot prove two transactions were ever genuinely open on PostgreSQL at the same time — either pattern can pass on scheduling alone. Slice 3 explicitly committed to closing this; slice 2's own review accepting a probabilistic test was never a waiver carried forward. New file `apps/network-api/tests/test_interleaved_concurrency.py` adds four tests that hold one transaction open with a `flush()`ed, uncommitted write, launch the conflicting operation through the real app as a background task, and prove — via a timeout that the task must NOT clear while the first transaction is open — that it is genuinely waiting on PostgreSQL's own lock, not merely slower: both namespace-guard orderings (root-first, delegation-first), a rollback variant (the blocked transaction is correctly released and succeeds once the holder rolls back, never left stuck), and the thumbprint reservation-release-vs-publication race. Each asserts the constraint outcome, ledger consistency (exactly the events expected from whichever side won, with the losing side's row confirmed absent), and — for the rollback case — that the waiting transaction actually proceeds. All four pass locally (SQLite also exhibits genuine blocking here) and are pending CI confirmation against real PostgreSQL.

**2. Receipt binding — CONFIRMED GAP in documentation, now disclosed; no code defect.** Reading `proofs._artifact_digest` directly confirms it is a property of artifact **content only** — independent of which key signed it. Two different valid signatures over identical content produce an identical `artifact_digest`; the digest alone cannot distinguish "which proof was checked" from "which content was checked." This was true of the implementation before this review and remains true after it — what was missing was the explicit disclosure. `evidence.py`'s module docstring and this ADR's invariant A paragraph above now both state this plainly: `kid_used`/`delegated_kid` are what actually identify which signature was checked, and it is the *combination* with `artifact_digest`, never the digest alone, that disambiguates a substituted proof. Two new tests prove both halves directly (`test_altered_content_with_otherwise_identical_signing_produces_a_different_digest`, `test_substituted_proof_over_identical_content_shares_a_digest_but_differs_in_kid_used`), and confirm an accepted receipt's digest is recomputed from verified content at verification time (`proofs.py:284`/`312`), never trusted from an unverified claim.

**3. Rotation scope — CONFIRMED: the lifecycle primitive already works; only operator automation is missing.** Read directly: `GET /jwks.json` serves *every* non-revoked, time-valid root key for an organization (`status != "revoked"`, not `status == "active"` only), and nothing blocks registering a second root key while the first remains valid — so multiple concurrently-live root keys, and (per ADR-017, unchanged) multiple concurrently-live delegations per agent, already work via existing primitives alone; cutover is already an explicit operator action (`POST .../signing-keys/{kid}/revoke`), not automatic. The one real inaccuracy found: ADR-018's own prose describes a `"rotating"` status distinct from `"active"`, but no code path anywhere ever creates or checks for a literal `"rotating"` value — `register_signing_key` always writes `"active"`, and `/jwks.json`'s `!= "revoked"` filter never needed the distinction to begin with. This is a documentation inaccuracy, not a missing capability. New test `test_manual_root_rotation_runbook_overlap_then_explicit_cutover` (`packages/message-integrity/tests/test_root_rotation_overlap_and_cutover.py`) drives the exact sequence a human operator could already perform today — register an incoming key while the outgoing key stays live (both verify, proving the overlap window), explicitly revoke the outgoing key (proving cutover is deliberate, not automatic), confirm the outgoing key's artifact no longer verifies while the incoming key's does. "Key rotation deferred" (as stated above) is accurate only for operator-facing automation (a script/cron walking through this sequence) and for the unused `"rotating"` status label — never for the underlying lifecycle operation itself, which this test now proves rather than assumes.

**4. The widened `ProofError` catch — CONFIRMED GAP, now fixed in both the delegation and plain-artifact paths.** Tracing the exact exception flow: `HttpDelegationResolver._fetch`'s per-token `except ProofError: continue` only ever wraps the call to `verify_delegation_token` — the surrounding `delegations.json` HTTP fetch and `response.raise_for_status()` were never inside it and already failed closed correctly. The real gap was one level deeper: `verify_delegation_token`'s (and, found during this review, the plain-artifact path's `verify_artifact_proof`'s) root/org-key resolution step caught `except Exception` around `jwks_resolver.get_key(...)` — a BLANKET catch that converted not only a legitimate "this kid is revoked/expired/never existed" (`KeyNotFoundError`) into a per-token rejection, but *also* a genuine infrastructure failure of the JWKS fetch itself (network-api unreachable, a timeout, a malformed response) into the exact same thing. For `HttpDelegationResolver`, this meant a root-JWKS outage affecting every delegation in a list would make `_fetch` return an **empty dict**, indistinguishable from "this organization genuinely has no delegations" — a dangerous fail-open-by-omission for the one case that most needs to be loud, not silent. **Fixed** by narrowing both catches to `except KeyNotFoundError` specifically (the one semantic signal every `JwksResolver` implementation raises for "no valid key"); every other exception now propagates with its real cause intact, out through `_fetch`'s per-token loop (which no longer matches it as a `ProofError`), failing the whole lookup closed with a diagnosable error rather than a silently empty result. New test `test_root_key_infra_failure_propagates_not_empty_list` (`packages/message-integrity/tests/test_delegation_resolver_freshness.py`) proves this with a fake resolver whose `get_key` raises a non-`KeyNotFoundError` exception, asserting the lookup raises (and specifically is *not* `DelegationNotFoundError`) rather than resolving to "not found."

## ADR-019 — M8 slice 4 design (external-agent onboarding and trust boundaries): server-owned authentication mode, a scoped and introspectable org-admin credential, a corrected four-layer trust model, and rollback that never falls back to the legacy path (2026-11-26, M8 slice 4 — PLANNING ONLY, not yet implemented)

**Status: design under review; not yet approved for implementation.** The first draft of this ADR proposed replacing the single global `network_admin_api_key` (confirmed, by reading `app.py`, to gate every organization-management action in `network-api` today — `issue_agent_management_credential` at `app.py:301`, `add_member` at `app.py:962`, and the same pattern for signing-key rotation and delegation publication) with a new org-scoped admin credential, authorized by a request-level "external" flag and a bare jti/iat confirmation call. Review found six ways the old authority could survive alongside the new one, or the new one could be weaker than it looks. This revision closes each.

### 1. The authentication boundary is server-owned state, never a request flag

**`OrganizationRecord` gains a server-held `auth_mode: "legacy_global_key" | "org_scoped_credential"`**, set only by the bootstrap/recovery sequence in §3 below — never by any field in an ordinary management request, and never inferable from which credential happened to be presented. Every management endpoint's FIRST step, before looking at any credential at all, is: resolve `organization_id` from the URL path, load that organization's stored `auth_mode`, and enforce exactly one path for it:

- `auth_mode == "legacy_global_key"`: only the global key authorizes. An org-scoped credential — even a validly-issued one for a *different* organization that happens to also have `auth_mode == "legacy_global_key"`, which cannot exist, since no such credential is ever issued to a legacy-mode org in the first place — is never accepted.
- `auth_mode == "org_scoped_credential"`: only that exact organization's own scoped credential authorizes. **The global key is structurally rejected for this organization, even when presented correctly** — not merely "not required," but refused outright, so there is no path by which old authority quietly continues to work for an org that has moved to the new model.
- **Changing `auth_mode` itself is never reachable from any ordinary management endpoint** — it is exclusively a bootstrap/recovery operation (§3), with its own distinct audit event type, never a side effect of any credential-authorized call.

### 2. Org-admin credential: lifecycle, blast radius, and what it explicitly is not

**This is a v1 machine-admin mechanism — explicitly not human OIDC, not member-level RBAC, and individual human accountability within an onboarded external organization is deferred, stated plainly rather than implied solved.** If that organization wants per-human attribution for its own staff, that is the organization's own internal concern to build on top of this credential, not something this slice provides.

- **Audience:** bound to exactly one `organization_id` at issuance — unusable for any other.
- **Scope, enumerated, not "everything the global key could do":** `manage_members`, `read_members`, `issue_service_credentials` (itself sub-scoped — this credential may only mint `manage_agents`/`use_*_tools`-tier service credentials, never a credential carrying more authority than itself), `rotate_signing_keys`, `publish_delegations`, `revoke_delegations`, `read_key_events` (added after the first review found three organization-management-adjacent endpoints omitted from this ADR's own matrix — see the correction below; `read_members`/`read_key_events` close two of those three). **Explicitly excluded, with no path to acquire via this credential under any circumstance:** platform bootstrap (creating new organizations), `auth_mode`/classification changes, any action touching another organization, and — deliberately, unlike the other five scopes — OIDC-tenant-mapping writes, which belong exclusively to the separate operator/recovery authority for every organization, not to this credential at all (see the correction below).
- **Expiry:** configurable, default 90 days, hard maximum 1 year — renewable only by explicit re-issuance (itself an audited event), never silently auto-renewing.
- **Storage:** `network-api` stores a salted hash of the credential secret (or, if implemented as a signed token, stores its unique issuance-record identifier and live status) — **never a recoverable plaintext secret.**
- **Delivery:** exactly once, in the single bootstrap/rotation response that creates it — never retrievable again afterward; loss requires a fresh rotation, which invalidates the old one.
- **Rotation:** self-service — the organization rotates its own credential by presenting its current valid one; this does not require AIMO-operator involvement for the routine case.
- **Revocation:** either self-service (organization revokes its own), or AIMO-operator-forced via the separately-authenticated recovery path in §3 (compromise response) — **never through the credential being revoked itself**, since a compromised holder must not be able to block AIMO's own forced revocation by, say, racing to use the credential one more time; forced revocation is a recovery-authority action, structurally independent of the credential it's revoking.
- **Audit attribution:** every action is logged as "organization `{id}`'s admin credential," not a named human — consistent with this being an org-level, not person-level, mechanism.

### 3. Bootstrap and recovery: separately authenticated, audited, and the only place `auth_mode` changes

A distinct operator-facing sequence, authenticated by a mechanism separate from both the global key and any org-scoped credential (an AIMO-operator-held credential, itself not shared with any organization, external or otherwise — the exact mechanism, e.g. a human-held operator OIDC role on an internal tool, is an implementation detail for this slice to pin down, but it must not be the same secret as either of the two paths it's arbitrating between):

1. **Create** the `OrganizationRecord` (unchanged mechanism) with `auth_mode = "legacy_global_key"` by default.
2. **Bootstrap to external** (operator action, audited): sets `auth_mode = "org_scoped_credential"` and, in the same operation, issues that organization's one-time-delivered admin credential. This is the only code path that ever sets `auth_mode` to `"org_scoped_credential"`.
3. **Recovery** (operator action, audited, usable at any time, not just at bootstrap): force-revoke and reissue an org's admin credential; force-revert `auth_mode` back to `"legacy_global_key"` if an organization needs to fall back under direct AIMO operational control (e.g., a compromised org that can't safely rotate its own credential) — this still never permits the *global* key to act on that organization silently; it is an explicit, audited mode change, after which the global key legitimately works again for that one organization until it is bootstrapped forward again.

### 4. Confirming the exact issued credential — introspection, not a bare jti/iat check

The first draft's "ask network-api if this jti was issued" is forgeable by anyone who also holds the shared HMAC secret, since they could construct a different credential reusing a known/guessed `jti` with different claims around it. **Corrected design: move the organization-facing and cross-service credentials used in this slice to an opaque, introspection-only model (RFC 7662-shaped, not a new invention) rather than a locally-verifiable self-contained token.** The token itself carries no claims — just a high-entropy, unguessable reference ID. `registry-api` (or any other verifier) never evaluates it locally; it always calls `network-api`'s introspection endpoint, which returns the authoritative claims from its own stored issuance record: issuer, audience, `organization_id`, subject (`agent_id` if bound), scope, validity window, and current revocation state — all in one response, so there is nothing left for a holder of any secret to forge, because there is no local verification step at all to feed a forged value into. **Required of every introspecting call:** TLS (stated explicitly, correcting the first draft's implicit conflation — **HMAC is message/transport integrity for the token's own payload, it is not transport security; introspection calls between services require TLS regardless**), a separate service-to-service authentication mechanism for the introspection call itself (this one may legitimately remain a shared secret, since it is AIMO-internal infrastructure-to-infrastructure traffic, not organization-facing — the forgery concern this section exists to close is organization-facing, not infra-to-infra), and fail-closed behavior on timeout, a malformed response, or any claim mismatch — ambiguity is always a rejection, never a best-effort accept.

**Revocation bound:** since every check is already a live call (no local cache to go stale), revocation is visible to the very next introspection call — essentially immediate, bounded only by **the same residual check-to-use race ADR-018 already named for delegations and explicitly declined to solve there**: a credential introspected as valid, then revoked a moment later, can still complete whatever action it was already mid-flight authorizing. This is not newly solved here either — named as the same class of residual risk, not a new one.

### 5. The fourth trust layer, corrected

**A trading relationship establishes counterparty *eligibility* — it does not, by itself, authorize any specific transaction.** A given commitment additionally requires: the artifact's type is within the presented delegation's scope (ADR-017), a live (not stale-cached, for commitment-adjacent types) identity/delegation check, an OPA policy decision, any required human approval (ADR-011's existing flow), and the commitment protocol's own two-round-trip semantics (ADR-011) — none of which the relationship check substitutes for. **Separately: endpoint and key control establish control of a key and an endpoint — they establish nothing about the *legal* identity of the organization behind them.** Verifying someone holds a given private key and controls a given URL is not a KYC or legal-identity determination, and nothing in this system claims it is. Both limits are stated explicitly in the public OpenAPI contract's prose (§6) and covered by tests (§8), not left implicit.

### 6. The Trust Extension is a declaration, never self-asserted evidence

An Agent Card's Trust Extension descriptor may advertise which capabilities a party supports and *where to verify them* — it must never be treated as itself proving "verified identity," "active delegation," or "permission to trade." A verifier always calls the actual authoritative source — `registry-api` for identity, `network-api` for delegation and relationship status — and never trusts a status flag embedded in the discovering party's own self-published card. The descriptor carries its own schema version (independent of `trade_protocol`'s version); lookups against the authoritative sources follow the same freshness/fail-closed rules as elsewhere in this system. **Access control, specifically for relationship queries:** whether organization A and organization B have an active trading relationship is commercially sensitive information (it can reveal a competitor's supplier relationships) — a relationship-existence query is answerable only to one of the two organizations actually party to it (or an AIMO operator), never as an open "does X have a relationship with Y" lookup answerable by an arbitrary third party. Identity and delegation checks remain broadly checkable by any counterparty attempting to verify a sender (that's their purpose); relationship checks are scoped tighter, deliberately.

### 7. Rollback never silently falls back to the legacy path

**Disabling `external_onboarding_enabled` gates new bootstrap only — it never changes any existing organization's `auth_mode`.** An organization already bootstrapped to `"org_scoped_credential"` keeps requiring its own scoped credential indefinitely; the flag going false does not, and structurally cannot, cause the global key to start working for it again — that would recreate exactly the "old authority survives" problem this whole ADR exists to close. If AIMO genuinely needs to revert a specific organization to legacy mode, that is §3's explicit, audited recovery operation, never an automatic consequence of the flag. **Disabling the onboarding gate is explicitly not the same as revoking anyone already onboarded:** existing external agents' discovery, identity-verification, and trading-relationship status are entirely unaffected by the flag — revocation remains its own explicit action via the existing `registry-api`/`network-api` revoke endpoints, never a side effect of toggling onboarding.

### Acceptance tests (extended; supersedes the original 9-test list)

1. Credential-vs-`auth_mode` alias test: the global key, presented against an org whose stored `auth_mode` is `org_scoped_credential`, is rejected — regardless of any request-level flag.
2. Mixed-credential test: org A's scoped credential presented against org B's URL path is rejected at `network-api`, independent of registry-api.
3. `auth_mode` is never changeable via any ordinary management endpoint, under any credential — only via the dedicated bootstrap/recovery path, and that path is itself independently authenticated and audited.
4. Enumerated-scope test: an org-scoped credential cannot mint a service credential with more authority than its own `issue_service_credentials` sub-scope permits, cannot touch another organization, and cannot reach platform-bootstrap or classification-change endpoints under any circumstance.
5. Credential storage: the stored record never contains a recoverable plaintext secret; a database read of the issuance table cannot reconstruct a usable credential.
6. One-time delivery: the credential value is returned exactly once, in the issuance/rotation response, and is never retrievable again by any subsequent call.
7. Self-service rotation invalidates the prior credential atomically with issuing the new one.
8. Forced recovery-revocation succeeds even when attempted against an organization whose own credential is presumed compromised/unresponsive — proving recovery authority doesn't route through the credential it's revoking.
9. Introspection claim-substitution test: a holder of the shared service-to-service secret cannot construct a token that introspects as belonging to a different organization/scope than what was actually issued — because the opaque reference carries no claims to substitute around.
10. Introspection fails closed on timeout, malformed response, and claim mismatch.
11. The fourth-layer test: a valid trading relationship alone, with an out-of-scope artifact type, or without a required approval, does not authorize a commitment — each independent requirement is tested to actually gate, not just the relationship.
12. Trust Extension descriptor self-asserting "verified"/"active"/"authorized" is never trusted — a verifier that ignores the authoritative lookup and trusts the card's own claim is the thing under test (i.e., test that the verification code path always calls the authoritative source and never short-circuits on the card's self-reported status).
13. Relationship-query access control: a third party uninvolved in a relationship cannot query its existence; either actual party (or an operator) can.
14. Pre-bootstrap gate: `external_onboarding_enabled=false` blocks new external-org bootstrap end-to-end.
15. Post-bootstrap rollback: `external_onboarding_enabled=false` after an org already exists as `org_scoped_credential` leaves that org (and its agents' discovery/trading status) completely unaffected — still requiring its own credential, never falling back to the global key.
16. `network-api` unreachable during an introspection call fails closed within a bounded timeout — not fail-open.

### Explicitly unchanged
Endpoint/key-control mechanics (ADR-015/016), delegation scoping/revocation (ADR-017/018), and the trading-relationship mechanism's own data model (ADR-008) are reused as-is; only how authority to *act* on an organization's behalf is established changes in this slice. Issue #4 is not folded into this slice.

### Implementation notes (2026-11-26)

**Endpoint inventory, verified against actual code before implementation, as instructed — two corrections to the matrix above:**

1. **No `POST /organizations` create endpoint existed at all before this slice** — organizations were previously created only by seed data or test fixtures, never a live API call. This slice adds it (gated by the new operator authority), rather than merely re-gating something pre-existing.
2. **Delegation revoke/release-reservation are keyed by `jti`, not `kid`** — the ADR's matrix row said `{kid}`; the real, pre-existing route is `/organizations/{organization_id}/delegations/{jti}/revoke` (a delegation's `jti` is its own unique identifier; `kid` identifies the *key*, which can appear in more than one delegation across its lifetime). A third pre-existing endpoint the original matrix omitted entirely, `/delegations/{jti}/release-reservation` (ADR-018 §5), is now folded into the `revoke_delegations` scope alongside `revoke_delegation` — both are lifecycle-ending actions on a delegation, not creation.

**Server-owned `auth_mode`, implemented exactly as designed:** `OrganizationRecord.auth_mode` (migration `0007`, default `"legacy_global_key"` for every existing row — conservative backfill, never silently upgrading anyone). `_resolve_org_authority` is the first thing every gated endpoint calls, before any credential is even parsed; an unrecognized/missing mode raises 403, never falling through to the legacy path. Wired into all eight matrix rows this ADR actually governs: `issue_agent_management_credential`, `register_signing_key`, `revoke_signing_key`, `publish_delegation`, `revoke_delegation`, `release_thumbprint_reservation`, `add_member`, `revoke_member`.

**Bootstrap/recovery authority:** a third, distinct secret, `network_operator_key` (`_require_operator`), gates `POST /organizations` (create), `POST /organizations/{id}/bootstrap-external`, `POST /organizations/{id}/recovery/force-revoke-credential`, and `POST /organizations/{id}/recovery/revert-to-legacy` — never the same check as `_require_admin` or any organization's own credential, and no code path lets an org-scoped credential reach any of these four endpoints (they don't accept `Authorization: Bearer` at all).

**Org-scoped admin credential, implemented exactly as specified:** `OrganizationAdminCredentialRecord` stores only a salted SHA-256 hash (`network_api.credential_hash`) — the secret itself (`secrets.token_urlsafe(32)`) is returned exactly once, in the `bootstrap-external`/`admin-credential/rotate` response body, and is never reconstructible from the stored row. Rotation (`POST /organizations/{id}/admin-credential/rotate`) requires presenting the *current active* credential; a revoked row fails that check and therefore cannot mint its own replacement (new requirement, verified by `test_revoked_credential_cannot_issue_its_own_replacement`). Forced recovery-revocation (`force-revoke-credential`) takes only the operator key — no credential of the organization's own is ever read or required, so a compromised/unresponsive organization's credential can still be shut off.

**Opaque, introspection-only `manage_agents` credentials, scoped deliberately narrow:** only the one credential `registry-api` verifies (`manage_agents`) was moved to the new opaque reference-ID format (`svc_<token>.<secret>`, `ServiceCredentialIssuanceRecord`, hashed the same way as the org-admin credential). Every other scope (`use_buyer_tools`, `use_supplier_tools`, `execute_order`, `manage_organization`) keeps the pre-existing self-contained HMAC format, completely unchanged — this slice's forgery concern is specifically the one credential a *different service* verifies without ever calling back to its issuer; the other scopes are verified by the same organization that could mint them anyway, so moving them would add migration risk without closing a real gap. `registry-api.require_org_bearer` detects the format by its `svc_` prefix and calls `POST /introspect` instead of local HMAC verification for that one case; any other token shape still uses the original path, so every pre-slice-4 agent and every `legacy_global_key` organization is completely unaffected.

**`/introspect` response schema, exactly:** `{active: bool, organization_id: str | None, scope: str | None, agent_id: str | None, issued_at: str | None, expires_at: str | None, revoked: bool | None}` — no credential hash, no salt, no internal row ID, no bearer secret, ever. Authenticated by `X-Internal-Service-Key` (the existing `network_internal_service_key`, already shared between the two services for the pre-existing relationship lookup — reused, not a new secret, per ADR-019 §4's explicit allowance that infra-to-infra traffic may remain a shared secret). The raw token is never logged by any application-level log statement (verified by `test_introspection_never_logs_the_raw_token`, which deliberately excludes the DB driver's own DEBUG-level SQL-parameter echo — a pre-existing, out-of-scope property of every parameterized query in this codebase, named here rather than silently ignored).

**Revocation-freshness bound, stated precisely as instructed:** every `registry-api` call that hits the opaque-credential path performs a live introspection call — there is no cache on that path to go stale, so a revocation is visible to the *very next* call, full stop. The one residual risk is exactly the check-to-use race ADR-018 already named for delegations and explicitly declined to solve there: a credential introspected as active a moment before a forced revocation lands can still complete whatever single action was already in flight. Nothing in this slice changes that; it is named, not solved, here either.

**What this slice did NOT implement, stated plainly rather than left to be discovered:** ADR-019 §5 (Trust Extension as declaration) and §6/§8 (relationship-query access control) describe a design — no Trust Extension descriptor and no relationship-query-specific access control were added in this slice's code. The existing `/relationships` endpoint (unchanged) is unauthenticated for the GET case beyond the internal-service-key path registry-api already uses; a dedicated access-controlled relationship-existence query for organization-facing callers remains unbuilt. This is a real gap against the ADR's own text, named here rather than claimed done — tracked as a follow-up in TASKS.md below, not silently folded into "explicitly unchanged."

### M8 slice 4 completion (2026-11-27) — publishing the public contract before slice 5, per explicit sequencing

**Why this work exists as its own unit, not folded into slice 5:** slice 5's purpose is proving an independently-built, non-Python agent can integrate with AIMO BRAIN using only the published public contract — no internal Python packages, no database access, no global admin key, no shared HMAC secret. Building that reference agent before the contract itself was published and verified standalone would only prove "an agent built with knowledge of AIMO's internals can talk to AIMO," not genuine interoperability. This closes the two items ADR-019's first merge-readiness review explicitly disclosed as designed-but-not-implemented (§5/§6/§8), and verifies the resulting contract is actually sufficient before slice 5 depends on it.

**Published:** `docs/specs/external-integration-openapi.yaml` (OpenAPI 3.1) — exactly the subset of `registry-api`/`network-api` an external integrator needs: discovery (`GET /agents`, `GET /agents/{agent_id}`, `/agents/{agent_id}/verify-sender`), verification (`verification/start`/`confirm`), the public unauthenticated `jwks.json`/`delegations.json` reads, the org-scoped-credential-authenticated management routes from the authorization matrix above, and the new relationship-status route below. It deliberately omits every AIMO-internal-only surface (`network_admin_api_key`, `network_operator_key`, `network_internal_service_key`, `registry_admin_token`) — none of the three secrets an external integrator must never hold appears anywhere in this document, by omission, not by redaction. Its own prose states the four-layer trust model (discovery / verified identity / signing delegation / permission to trade), names each layer's authoritative source, and states the freshness/fail-closed rules — not bare endpoint shapes.

**Published:** `docs/specs/trust-extension.schema.json` + `docs/specs/trust-extension.md` — the declarative Agent-Card extension (A2A `AgentExtension`, `uri: https://aimo-brain.dev/extensions/trust/v1`). Structurally declarative only: the schema has no field named `verified`, `active`, or `authorized` — only `supported_capabilities` (which of the four layers this party claims to support) and `verification_sources` (where to independently check each one). This is a deliberate structural choice, not a documentation promise: there is no field for an implementation to be tempted to read a status off instead of calling the authoritative source. Its own `schema_version` is independent of `trade_protocol`'s artifact version and the JWS spec's version.

**Relationship-access-control, implemented, not merely designed:** a new endpoint, `GET /organizations/{organization_id}/relationship-status/{counterparty_organization_id}` (`apps/network-api/src/network_api/app.py`, `get_relationship_status`, plus `RelationshipStatusOut`), deliberately separate from the two pre-existing `internal_service_key`-gated relationship-listing routes (`GET /relationships`, `GET /organizations/{id}/relationships`), which remain unchanged for the portal's/registry-api's own trusted-backend use and were never the gap — the gap was that no organization-facing route existed at all. The new route is answerable only to (a) an AIMO operator (`X-Operator-Key`, bypasses per-organization authority entirely), or (b) one of the two actual parties, authenticated via `_resolve_org_authority` with a new `read_relationships` scope added to `ORG_ADMIN_CREDENTIAL_SCOPES`. The access control is structural, not a permission check bolted onto an open query: the caller authenticates AS `organization_id` in the path, and the stored query only ever matches rows where that same `organization_id` is a party — a third organization cannot phrase a query naming two *other* organizations at all, because it can only ever authenticate as itself. Response shape (`RelationshipStatusOut: {exists: bool, status: str | None}`) is deliberately minimal — no internal relationship id, no timestamps — distinct from the internal `RelationshipOut` the portal/registry-api receive. Test: `test_relationship_status_route_authorization_matrix` (`apps/network-api/tests/test_external_onboarding.py`) — a party querying its own side, the other party querying from its own side, an operator querying any pair, external global-key rejection, cross-organization credential misuse, an unrelated third organization structurally unable to phrase the A↔B query (correctly returns its own, unrelated `exists: false` rather than ever disclosing the real pair), and missing/unknown `auth_mode` denying rather than defaulting to legacy.

**Verification result: the documented flow is fully achievable using only the public contract. No blocking finding.** `tests/integration/test_external_integrator_public_contract_e2e.py` boots real `network-api` and `registry-api` servers (genuine HTTP over real sockets, `uvicorn` in background threads, not `ASGITransport`) plus a minimal third server standing in for the external integrator's own agent endpoint. After one operator-authenticated bootstrap call (onboarding is explicitly not self-service — this is the only step using AIMO-operator authority, never the integrator's), every subsequent step uses only: the integrator's own org-scoped credential, HTTP calls to exactly the routes the published OpenAPI document lists, and `cryptography`/`pyjwt` directly for key generation, JWK encoding, and JWS signing — the same third-party primitives an independent, non-Python-aware implementer reading only `docs/specs/jws-artifact-signatures.md` and the OpenAPI document could use. No `message_integrity`, `trade_protocol`, or `identity` import appears anywhere in the walkthrough. The test drives: root-key registration, minting an opaque `manage_agents` credential, agent registration with a signing key, both the endpoint-control and private-key-control verification challenges (the agent's own stand-in server genuinely serves the well-known challenge; the private key genuinely signs the key challenge), publishing a delegation built by hand with `pyjwt`, confirming the published root key and delegation are visible through the public, unauthenticated `jwks.json`/`delegations.json` reads, querying relationship status with the integrator's own credential, and confirming discovery works — plus a negative control proving the global admin key is rejected for this now-externally-onboarded organization even from the integrator's own vantage point.

**A real, if minor, discrepancy found and fixed during this verification — the exact kind of gap this exercise exists to catch:** the first draft of the OpenAPI document described `delegations.json`'s `delegations` array as pre-parsed metadata objects (`delegated_kid`, `scope`, validity timestamps). Running the actual walkthrough against the real endpoint revealed the array is a list of raw JWS compact tokens — a verifier decodes each one itself to read those claims, per the JWS spec. **This published document's claim about network-api's actual response shape was simply wrong until this verification ran it for real** — fixed in the schema and documented explicitly, rather than left as an inaccuracy a future external implementer would have discovered the hard way.

**A configuration-leakage bug introduced and caught by this same work, not shipped:** the first draft of the new e2e test set `EXTERNAL_ONBOARDING_ENABLED=true` via a bare `os.environ[...]` assignment instead of `monkeypatch.setenv` — this leaked the override into every test run afterward in the same pytest process and broke `test_external_onboarding.py`'s own flag-default assertions when the two files ran together. Caught by running them together before considering this done (never assume a new test file in isolation proves nothing else broke), fixed by switching to `monkeypatch.setenv` throughout, matching the pattern every other test in `test_external_onboarding.py` already uses for exactly this reason.

**A real, systemic test-infrastructure issue found and worked around while landing this fix, named rather than silently patched over:** an initial version of this fix added sixteen new tests, one scenario per test, each calling `_fresh_app_with_orgs`/`create_app()` independently. CI's `python` job failed twice in a row — reproducibly, not intermittently, always the same nine `registry-api` tests, always `sqlalchemy.exc.OperationalError: ... FATAL: sorry, too many clients already`. Root cause: `create_app()` constructs its own internal SQLAlchemy engine, disposed only via the FastAPI app's ASGI lifespan `finally` block (`app.py` around line 394) — but every test in this file (and this whole test suite) drives the app through `httpx.ASGITransport` directly, which never runs ASGI lifespan startup/shutdown. That internal engine's connections are therefore never explicitly returned to PostgreSQL for the rest of the pytest session; this is a pre-existing property of every test that calls `create_app()` across the entire suite (438 tests' worth, already in place before this fix), not something this fix introduced. It was already, apparently, close to PostgreSQL's `max_connections` ceiling; adding sixteen more such tests tipped it over, consistently, at the same point in collection order every time. **Resolution within this fix's own scope:** the sixteen single-scenario tests were consolidated into three tests (one per route), each sharing one `create_app()`/engine/client across every one of its route's required scenarios via multiple pre-seeded organizations for isolation — net three new leaking engines instead of sixteen, enough headroom to pass CI twice. **Fixing the underlying leak for the whole suite — e.g. adopting `asgi-lifespan`'s `LifespanManager` around every `ASGITransport` usage, or restructuring `create_app()` to accept an externally-owned engine disposed elsewhere — is real, separate work, not done here and not claimed done.** Recorded as a residual risk in TASKS.md below: the suite is now closer to this ceiling than it was, and the next several hundred tests added by any future slice should budget for it.
